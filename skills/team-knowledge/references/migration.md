# 迁移指南：从 .codestable 与 .team-workflow 到 .tw

由代理整理，不使用脚本。新工具不读取旧格式；项目只保留现在仍成立的设计，但放弃过的做法与教训必须保留。

## 步骤

1. **准备**：在新分支上进行，工作区干净；在途的团队任务先完成或明确放弃；本仓所属产品组已换装新技能，并卸载 `cs`、`cs-analysis`。高风险结论的守护测试需要数据库等环境时，先确认迁移代理能运行这些测试；不能运行时，由主代理在可运行的环境中执行，把原始结果交给迁移代理。
2. **初始化**：`tw init --apply`。把 `.team-workflow.json` 的检查配置整理进 `.tw/config.json`，原文登记整理进 `documents`；本机跨仓路径写进 `.tw/local/repositories.json`。
3. **整理知识**：直接阅读旧的当前卡片、`PROJECT.md`、分类摘要、documents 登记和被取代的卡片。逐条按下文核实后，用新格式和新的表述写成 rule、decision、lesson、glossary、overview。
   - 历史决策按现行设计重写；被取代的卡片及取代理由、曾被接受但已被代码否定的结论，写进对应决策的“放弃过的做法”。
   - 跨仓重复的内容只写在契约提供方的仓库，其他仓用 `related` 引用。
   - 丢弃一次性结果、任务流水、工具版本和空模板。
4. **清理**：删除已跟踪的 `.codestable/` 和 `.team-workflow.json`；未核实的旧内容不另存，迁移说明列出旧路径，原文仍可从 git 历史取回。未跟踪的 `.team-workflow/` 证据和 `.codestable/cache`，先列出体积，用户同意后再删除。
5. **收尾**：`tw init --guidance --apply` 更新指引块；AGENTS.md、CLAUDE.md 中要求使用旧 CS 的段落手工删除（`tw check` 会提示）；删除根 `.gitignore` 中的旧条目；`tw check` 没有错误。
6. **PR**：正文写“迁移说明”，包括：保留、改写、删除的数量及理由类别；待用户确认的问题；未能核实、因此没有迁入的内容及其旧路径。用户确认后合并；需要回退时撤销 PR。

## 核实

| 范围 | 做法 | 不通过时 |
| --- | --- | --- |
| 全部迁入条目 | 阅读真实入口和关键路径，核对路径、符号、常量、错误码、协议字段和表结构。路径存在不算支持 | 不迁入 |
| 涉及权限、持久化、并发、消息、公开契约、跨服务的行为结论 | 运行守护测试或真实接口，用独立确定的预期核对 | 不迁入，列入迁移说明 |
| 业务规则与决策、无法执行验证的结论 | 用户在 PR 中逐条确认，确认记录写入 `source` | 不迁入，列入迁移说明 |
| 试点仓全部条目；后续批次的高风险条目及其余至少 20% | 由未参与迁移的代理对照代码复核 | 退回修改 |

跳过的测试、模拟或替身环境中的运行，只能证明它覆盖的部分，不算对真实行为的核实。独立复核在 PR 中写明：复核人、复核范围、发现的问题及处理结果。

核实时：

- 逐条阅读，不继承 current、accepted、PASS 等标签。
- 分别判断“应当怎样”和“当前怎样”。
- 每条记录支持证据、反证和未核实的部分。
- 不编造测试结果、批准人或日期。

## 多仓顺序

按“契约提供方 → 核心实现 → 消费者”逐仓迁移，每仓一个 PR。尚未迁移的仓，brief 显示为“尚未迁移”。
