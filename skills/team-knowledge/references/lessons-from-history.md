# 复盘与找回教训

## 定期复盘

回看一段时间内合入的提交，把返工与验证问题写成教训。节奏由项目决定，例如每周一次，或交给定时运行的代理；宜由未参与这些提交的代理或成员执行。

1. 确定范围：上次复盘 PR 说明写明的终点提交之后到当前主干；首次或找不到时取最近 7 天。出现记录中已写明的提交只计一次。
2. 逐个阅读提交说明、改动，以及关联的 Issue、PR、验收与复验记录，找三类问题：
   - 返工：同一问题修了又修，如重新打开的 Issue、回滚、同一处的连续修复、验收多轮才通过；
   - 不该合入：合入时检查未通过或缺少项目要求的验收，夹带目标以外的改动，未经用户确认推翻已确认的决策或重新采用放弃过的做法；
   - 验证太粗：没经过真实入口就称完成，去掉修复后守护的测试或场景仍然通过，说明里没写实际运行了什么。

   同时记下照着已有教训或规则做对的提交。
3. 每个发现用 `tw brief --task "<发生了什么>" --path <涉及的文件>` 查已有条目，按[写作规范](writing.md#出现与升级)处理：
   - 同一失败机制：追加出现记录，或把做对的提交写进做对的例子；
   - 新的机制：用 `tw new lesson` 写成教训，标题是一句要遵守的做法；
   - 教训出现满 3 个不同日期：升级为 rule。

   改写条目前核对当前代码，再更新 `verified`。
4. 运行 `tw check`，提交只改知识的 PR。说明写复盘范围（起止提交）、每个发现及其证据、新增与升级的条目，由用户确认后合并。

## 找回历史教训

在用户要求时执行。来源：

- 旧知识的 git 历史：`git log --diff-filter=D --name-only -- .codestable`，以及 `git show <提交>^:<路径>`。
- Issue、PR 和已有的复盘文件，例如 `history-review/`。
- 其他仓库的历史：迁入适用于本仓实现的教训，并写明适用条件。

做法：

1. 先列出候选：现象、根因、出处，交给用户确认范围。
2. 保留现在仍可能再犯的失败机制。逐条阅读当前代码，确认防护是否还在；能发现它的测试按 `仓库:文件#测试名` 写进 `guards`。
3. 用 `tw new lesson` 写成教训，`source` 指向原始提交或 Issue，`verified` 写实际核对时的提交。
4. 运行 `tw check`，在 PR 中列出采纳与放弃的候选，由用户确认。
