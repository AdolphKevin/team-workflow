# 团队协作与交付

从主技能开始或接手团队任务时使用本页。工具输入和字段见 [工具约定](contracts.md)。
首次独立验收、有效回归、端到端链路、运行环境和交付记录，统一按
[业务验收与质量改进标准](business-acceptance.md)执行。处理缺陷或每周复盘时也读取该标准
第 7、8 节及其引用；记录使用[交付验收](../templates/business-delivery.md)、
[缺陷复验与保护](../templates/defect-protection.md)、[每周质量复盘](../templates/weekly-quality-review.md)模板。

## 开工前

用 `tw brief` 读取知识和需求原文，查清真实起点、角色操作、完整业务路径及受影响入口、服务责任，再按可独立验收的范围拆分。方案写目标、非目标、实现方法、验收来源、验证方式和未决问题，分别评估复杂度与风险。简单任务用短方案，开发后合并评审；中等、复杂任务先由具名评审人批准，可用：

```bash
tw team approval-draft --task <任务文件> --design <方案> --reviewer <姓名> --confirmation <说明> --mode plan
```

平台上的方案、批准和任务块按已有授权发布。首次修改源码或委派实施前运行 `start`，读简报并确认实施条件。有效批准和分派在范围内复用；新入口、跨服务责任或业务规则变化时重审受影响部分。

## 四命令流程

```bash
tw team start --task <任务文件> --design <方案> [--approval <已有批准>]
tw team run --task <身份>
# 未参与实施的人填写返回的 review.md
tw team review --task <身份> --submit
tw team deliver --task <身份> --reason <不需要更新知识的理由>
```

身份为任务编号或完整 Issue 地址。`current.json` 固定记录材料；显式 `--context`、`--run`、`--review`、`--report` 等路径仍可使用。新上下文清空后续材料，接续保留；同一请求编号对应同一组输入，修改材料后用新编号。

`run` 在必需检查全部有可用的通过结果后自动准备评审稿，失败不生成，有效工作稿不覆盖。需要时仍可手动 `review`。失败、必要跳过、缺失用例不能通过业务验收；检查只证明其声明的范围。按业务验收标准保留原始结果、环境与独立执行证据，维护本机和 CI 入口。

## 填写与提交评审

评审人实际阅读需求、代码入口和原始结果，填写姓名、知识冲突处置、standards/spec 及逐项验收的结论和理由、问题处置。绑定区和自动结果保持原样；工具生成运行证据与文件指纹。人工观察的观察人、时间、操作、结果、数据和证据由人填写。也可用 `review --submit --file <路径>` 提交别处的 Markdown。

**提交保存意见，验收核查通过条件。** 格式完整且绑定有效的“不通过”意见或含 open 阻塞问题的评审可以提交，登记为当前评审；问题进入历史，即使本次验收失败仍保留，后续草稿继续带入。提交仅拒绝格式不完整或过期绑定。实施者或非独立观察人的意见可以保存，accept/deliver 仍拒绝其作为独立验收证据。

简单任务需要合并批准时，独立评审人在“批准方案与代码”填“是”，会以其为批准人生成当前方案、源码和选中运行的批准；填“否”或留空不生成。实施者意见可以保存，但不生成独立合并批准。具名批准不替代实际评审或业务验收；不通过项、未解决知识冲突和相关阻塞问题会逐项列出并阻止验收。修复后重跑检查，再逐项复核。

任务、源码、策略、章节或选中运行变化后，工具按前一轮逐文件指纹列出“变化”，预填上一轮或过期工作稿中的意见。旧稿按原字节归档；每个预填结论和人工观察均须明确改为“复核：已复核”，不自动沿用。人工观察内容由人确认适用或重新填写。已知问题的编号、负责人、影响和阻塞阶段保持不变；接受限制、延期或解决均需明确处置，延期还需跟进任务和范围调整。

## 要更新知识时

评审提交后先 `tw team accept --task <身份>`；通过后在同一分支按 team-knowledge 规范更新知识并运行 `tw check`，再 `tw team deliver --task <身份>`。根因不明显的缺陷写 lesson，难以逆转的选择写 decision，必须保持的行为写 rule；决定改变时保留旧做法及放弃原因。多个任务共用知识时只写一次，各自报告列出。

`deliver` 依次核查业务验收、生成列全 Git 知识差异的报告、最终交付；已有有效验收和报告直接复用。无知识变化必须给 `--reason`；失败停在对应步骤，保留失败记录。验收后源码、任务或材料变化需要重新核查，知识改动本身不使执行结果过期。

需单独查看或补充报告时，保留 `delivery-template --task <身份>` 和 `verify --task <身份>`；复制报告为新文件后可用 `--report` 显式指定。主需求仍覆盖完整业务路径，子任务通过不代表主需求通过。

## 状态与关闭 Issue

`tw team status --task <身份> --format text` 只读已有材料，不运行项目检查或环境命令。它列出当前有效的业务验收、交付记录路径、步骤及下一条命令；草稿不算评审完成，方案、批准、源码或配置绑定变化时相关步骤过期。平台收尾说明或交接是否已发布从平台记录读取，不根据本地草稿推断。

关闭 Issue 须同时满足：最终交付完成；收尾说明或完整实施交接**已发布**；交付报告记录 `close_authorization`，包含具名确认人 `confirmed_by` 和可核对的授权来源 `reference`。流程为：

1. `deliver` 完成交付并生成收尾说明；多人接力、跨仓或跨服务任务按约定准备实施交接。
2. 按已有授权发布收尾说明或交接，核对平台上的责任、未决问题和实际发布记录。
3. 在新的报告副本中记录关闭授权，使用 `verify --task <身份> --report <新报告>` 再核对；已有有效报告也可由 `deliver` 复用。授权不自动授予提交、发布等其他操作权限。
4. 工具只报告 `closable`，**不执行关闭**。全部完成时显示“已交付；关闭需要授权，工具不执行关闭”；有实际关闭授权的成员按团队约定操作。

## 跨仓与接手

构建依赖、实际修改仓库和联合验收服务分别登记，普通构建依赖不强制增加共同实施者。
核对版本组合、源码内容与生成步骤，避免只在本机未推送的依赖上能编译。源码、原始运行
报告和知识范围使用真实仓库及相对路径；前端任务不能用无关后端目录代替。

交接保留方案版本、批准范围、职责、验收、依赖、未决问题和下一步。`verified` 引用实际
运行或业务验收材料；共享原始材料包或导入已发布的 CI 结果，接手者缺少原件时保留缺口。
源码链接放在 `references`。平台工具仅生成草稿，发布前后按已有授权核对并行变化。

环境安排在实施前确认。共享中间件须有具体隔离依据；仅获得使用授权不能代替技术隔离。
未解决的环境条件阻塞对应验证，不阻止其他已经满足条件的独立工作。
