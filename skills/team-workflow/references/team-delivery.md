# 团队协作与交付

团队任务使用本页，字段和职责见[工具约定](contracts.md)。验收、回归、环境及记录按[业务验收标准](business-acceptance.md)；缺陷与复盘另读其第 7、8 节。模板：[交付验收](../templates/business-delivery.md)、[缺陷保护](../templates/defect-protection.md)、[每周复盘](../templates/weekly-quality-review.md)。

## 开工前

用 `tw brief` 读取知识和需求原文，查清真实入口、角色操作、完整业务路径、受影响服务和责任。方案写目标、非目标、实现方法、验收来源、场景引用、检查和未决问题，分别评估复杂度与风险；按[批准路径](designs.md#内容与依赖)准备本地方案或草稿变更请求，批准命令为：

```bash
tw team approval-draft --task <任务文件> --design <方案> --reviewer <姓名> --confirmation <说明> --mode plan
```

本地任务保留 `approval-draft` 生成的 `approval.json`，用 `start --approval <approval.json>` 传入，之后的开工会沿用。

任务存验收编号，内容以方案为准。修改或委派前运行 `start`，阅读简报与“待确认章节”的原因，执行返回的批准命令；默认范围、指定章节及发布和对账重启见[分节方案](designs.md#批准与变化)与[发布步骤](designs.md#发布与隐藏记录)。

### 沿业务链路分段

主需求沿业务链路拆成任务，方案的实施任务节按段排列，每段写明接通的起点与终点：

1. 第一段打通最薄的端到端路径：只接通主链路上的节点，每个节点取最简单的正向路径，从入口到终点全部接通；这些节点业务上的反向（无权限、对象不存在等）随节点一起验收。
2. 后续每段加深一个节点、补一类反向，或接通一条支线。验收节按节点引用场景，加深与支线的场景写在后续段新增的节点里。每段同样写明起点（角色从哪个入口、在什么前置状态下操作）与终点（谁在哪里看到什么结果）。跨服务的需求按服务间链路分段，例如退款需求先接通“买家申请退款，商家在后台同意，支付服务退回款项”，再补部分退款与拒绝，最后接通通知支线。
3. 每段实现完成后，在本段的真实环境中立即验收 `pending` 列出的场景，链路上的服务全部按真实方式运行；下一段的实现可以同时开始。
4. 每个段的交接写明本段接通的场景节点与核对方法，验收以场景经真实入口执行为准；开发中不产出单元、接口与集成测试。

场景粒度与数量见[场景粒度](business-acceptance.md#场景粒度)。

## 五步流程

准备任务 → 运行检查 → 场景验收 → 提交评审 → 交付。本地命令如下；场景格式与执行方法见[场景指南](scenarios.md)：

```bash
tw team start --task <任务文件> --design <方案> [--approval <已有批准>]
tw team run --task <身份>
tw team scenarios pending --task <身份>
# 独立执行者按清单执行
# 结果和证据放在仓库外或 .tw/local/ 下
tw team scenarios submit --task <身份> --results <结果文件>
tw team review --task <身份>
# 未参与实施的人填写返回的 review.md，再提交
tw team review --task <身份> --submit
tw team deliver --task <身份> --reason <不需要更新知识的理由>
```

`current.json` 保存材料，也可显式指定路径；换组与接续见[当前材料组](contracts.md#当前材料组)，修改输入后用新请求编号。`run` 的评审稿准备条件、运行选用和场景判定见[交付入口](contracts.md#五步交付入口)及[场景与证据](contracts.md#场景与证据)。

## 填写与提交评审

评审人阅读需求、代码入口、原始检查结果和预填的场景执行，填写姓名、知识冲突处置、规范与需求及逐项验收结论、理由和问题处置。绑定区和自动结果保持原样；另一处的稿用 `review --submit --file <路径>` 提交。

平台提交完整评审 Markdown 后，可用 `review --task <身份> --from-platform` 登记，或运行 `deliver` 采用平台与本地较新者；本地提交使用 `--submit [--file <路径>]`。来源、姓名独立性及原文核对见[评审约定](contracts.md#实施批准与代码评审)。

格式与绑定有效的“不通过”、未解决问题或实施者意见均可保存；问题进入历史和后续草稿。`accept`、`deliver` 核对通过条件与独立性。合并批准的填写见[交付入口](contracts.md#五步交付入口)。修复失败项和相关阻塞问题后重跑检查，再逐项复核。

绑定变化时原稿按原字节归档，工具列变化并预填旧意见；每项预填结论改为“复核：已复核”。复核字段、证据与问题身份见[逐项复核](contracts.md#变化后逐项复核)和[问题处置](contracts.md#问题处置与交接)。

## 要更新知识时

评审提交后先 `tw team accept --task <身份>`；通过后在同一分支按 [team-knowledge 的完成步骤](../../team-knowledge/SKILL.md#完成后)更新知识并运行 `tw check`，再 `tw team deliver --task <身份>`。多个任务共用知识时写一次，各自报告列出。

`deliver` 依次核查业务验收、生成列全知识差异的报告、核查最终交付；有效验收和报告直接复用，无知识变化给 `--reason`，失败停在对应步骤。材料变化的有效性见[记录绑定](contracts.md#记录绑定)。需单独补报告时，用 `delivery-template --task <身份>` 生成，复制为新文件后通过 `verify --task <身份> --report <新报告>` 指定。

业务验收范围和回归状态见[场景与证据](contracts.md#场景与证据)，整体交付条件见[业务验收标准](business-acceptance.md#5-交付报告)。

## 状态与关闭 Issue

中断后运行 `tw team status --task <身份> --format text`，阶段判定、记录报告方式与下一步见[状态约定](contracts.md#进度恢复与统计)。

关闭 Issue 的条件为：最终交付完成；收尾说明或完整实施交接**已发布**；报告记录 `close_authorization`，含具名确认人 `confirmed_by` 和可核对的授权来源 `reference`。步骤为：

1. `deliver` 完成交付，按[单人任务的收尾说明](coordination.md#单人任务的收尾说明)准备收尾或交接。
2. 按已有授权发布，核对平台责任、未决问题和实际发布记录。
3. 在新报告副本中记录关闭授权，用 `verify --task <身份> --report <新报告>` 核对；已有有效报告可由 `deliver` 复用。
4. 按[工具职责](contracts.md#工具做什么)和 `closable` 结论，由获授权成员关闭任务。

## 跨仓与接手

构建依赖、修改仓库、联合验收服务分别登记；核对版本组合、源码与生成步骤，以及接手者能取得的共享提交。源码、报告、知识范围使用实际仓库与相对路径，检查在对应仓库执行。

交接保留方案版本、批准范围、职责、验收、依赖、问题和下一步。`verified` 引用实际运行或验收材料，经共享原始材料包或导入已发布 CI 结果提供；接手者缺原件时保留缺口，源码链接放 `references`。字段和冲突处理见[任务协作](coordination.md)。

实施前确认环境；共享中间件填写具体隔离依据，解决隔离后执行对应检查，其他已满足条件的独立工作继续。
