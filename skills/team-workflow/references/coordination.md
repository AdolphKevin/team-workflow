# 任务协作与交接

方案记录保存要求的结构化签名。Issue 验收块与方案同步修改时，按对应验收节计算变化，无关章节的原批准继续使用；Issue 的其他说明或全局条件变化、历史签名不足时，需要完整复核。每条平台记录保留实际发布评论的账号 `recorded_by`，用于追溯由谁记录。

共享任务保存分节方案、具体评审人的确认和可追溯交接。工具只读取 GitHub，并生成可供
检查的评论草稿；发布仍使用用户已有授权。
方案结构与逐节变更规则见[方案与评审](designs.md)。

## 平台任务与方案

Issue 正文使用 `team-workflow-task` 代码块。外层字段是 `data_version: 1`、
`parent` 和 `task`；没有总任务时 `parent` 为 `null`。内层 `task` 使用当前任务
格式，在目标、基准提交、风险和验收条件之外增加：

- `design_id`：本任务引用的稳定方案编号。
- `section_ids`：本任务负责的方案章节编号，至少包含一个实施任务章节。
- `acceptance_scope`：主需求使用 `requirement`；子任务使用 `task`，内外层 `parent` 均指向同一主需求。
- 可选的 `paths`、`symbols`、`scopes`：读取项目知识时使用的实际范围。

任务验收的编号、结果描述及检查清单必须与所选实施任务引用的验收章节一致。
结果描述对应方案章节的 `body`，检查清单对应 `data.checks`。普通进度、指派和
评论时间不改变要求指纹；修改 Issue 正文中的要求会要求更新方案和交接。

方案以 `team-workflow-design` 评论追加。工具生成外层记录，包含方案正文、
发布者、当时的要求指纹、前一份方案评论及其内容指纹、整个先前记录历史的指纹。
方案负责人确认该记录。每次修订编号加一，原评论保留。

子任务可以引用总任务上的方案及批准，不需要复制这些评论。方案和评审草稿
应发布到方案所属的总任务，交接与日常进度发布到各自任务。

`team-workflow-approval` 评论保存批准人、结论和明确批准的章节指纹；确认依据
`confirmation` 可选，有会议纪要、聊天记录等依据时建议填写。批准人不必亲自发评论，可由
他人代为记录；`load` 的 `approval_records` 同时列出批准人和实际发布评论的 `recorded_by`，
用于后续追责。工具只把当次选择展开成确定的章节清单；整份批准不覆盖以后新增的章节。
工具不能证明批准人确实同意，代为记录的批准由团队按需抽查。

中等、复杂任务在相关章节获批并指派后实施。简单任务可以在简短方案完成后实施，
随后将方案、代码和实际验证记录一起评审；高风险简单任务仍须完成风险对应的检查。
工具不会把可接手状态表示为已经通过业务验收。

## 两类交接

`handoff --kind design` 表示方案负责人把工作交给实施者；`--kind implementation`
表示实施负责人交代实际完成情况。交接输入示例：

```json
{
  "creator": "alice",
  "owner": "bob",
  "done": ["方案与验收条件已确认"],
  "verified": [],
  "remaining": ["按方案实现加法"],
  "questions": [],
  "next": "实现 T1，运行 A1 对应检查。",
  "included_progress": []
}
```

`creator` 是实际确认交接的人，必须承担对应的方案或实施责任；`owner` 是下一位
接手者，须是当前 Issue 的被指派人，并在方案中具有明确责任。三项责任分别保留，
不能因为把工作交给 B，就把方案负责人和验收负责人也改成 B。`questions` 使用
[问题记录](contracts.md)中的稳定编号、影响范围、阻塞阶段和处置依据，
自动带入方案及历次交接的已知问题。有明确责任和下一步的剩余工作可以正常交接。

工具自动补充方案版本、已经批准的章节指纹、源码内容指纹及所有仓库的实际提交
和内容版本。源码需可从共享仓库取得；未共享的工作区改动、本机独有外部文件、
遗漏的依赖或不可访问引用会明确留下缺口。`verified` 使用实际执行或业务验收文件的
`{path, sha256}` 引用，工具重新读取原始报告；源码和说明链接放入 `references`，
只作为辅助资料，不能代替执行记录或证明业务通过。

配置中的外部仓库有三种职责：`build` 只作为构建输入，`modified` 表示本次需要
修改，`joint` 表示需要联合验证。三类均记录版本。构建输入不因此增加协作人；
修改和联合仓库须有对应任务、被指派人和交付依据。联合工作另外保留接口原文及
确认位置、联合验收责任人。显式提供依赖清单时不能漏掉配置中的任何仓库。

`start` 返回当前要求、完整方案与历史、评审结论、分别记录的责任、按实际路径
读取的知识简报（`tw brief`）、交接记录及待确认进度。它使用实际改动和源码内容核对批准与范围，
并在结束前再次读取平台，发现读取期间的新进度或指派变化。没有交接时仍可准备
方案和评审，但不能声明已具备完整接手材料。

平台任务开工后，使用 `--task <完整 Issue 地址>` 调用 `run`、`status`、草稿、验收、交付和交接命令。工具按 `current.json` 补材料，并重新读取平台；方案或批准更新时先重新 `start`。`handoff` 和 `progress` 仍需相应的实际交接或进度输入，命令只生成评论草稿。

## 进度、冲突与收尾

普通进度沿用 `team-workflow-progress` 记录：每条有唯一请求编号、记录中的作者和实际发布评论的 `recorded_by`。
相同编号、相同内容只计算一次；同编号不同内容形成冲突。接手结果列出
`pending_progress`。负责人读过并确认后，将其中的 `{id,digest}` 放进交接输入的
`included_progress`，后续交接自动保留这些引用。新贡献不能因为没有写进交接而消失。

方案、批准和交接都绑定前序记录与完整先前历史。并行发布、被编辑的前序、同一
版本的竞争内容会形成缺口；不按最后时间选择获胜者。GitHub 提供创建及编辑时间时，
已编辑的结构化评论也会留下缺口，包括尚无后继的最后一条记录。

确实读过冲突各方后，保留全部评论，在新草稿输入增加：

```json
{
  "resolution": {
    "history_digest": "读取结果返回的当前历史指纹",
    "reason": "说明如何合并各方内容、采用哪些决定、保留哪些问题"
  }
}
```

工具只有在该历史仍一致时才建立新的明确起点。旧评论继续保留；之后再编辑旧评论，
这个确认也会失效。方案、批准、交接分别整理各自的冲突，不能用一次交接消除
未确认的方案分歧。

## 接入已有 Issue

只有说明、没有 `team-workflow-task` 代码块的 Issue 会让读取平台的命令返回
`error_code: issue-not-adopted`。准备好任务（和共享方案）后运行：

```bash
tw team issue-draft --root "$PROJECT" --task "$TASK" [--design "$DESIGN"] \
  [--with-task "$SIBLING_TASK"] [--reviewer <评审人>]
```

结果按 Issue 给出新正文（原有说明逐字保留，只替换或追加结构化代码块）、方案所在 Issue 的方案评论、
给具体评审人的评审请求，以及发布顺序。共用父方案的子任务须写 `parent` 和 `acceptance_scope: task`。
工具不修改 GitHub；草稿按 `next_steps` 顺序由用户发布，评审人明确确认后再用 `approval-draft` 生成批准记录。

## 单人任务的收尾说明

交接有三类：方案交接（`design`）、实施交接（`implementation`）和收尾说明（`close`）。被指派人只有
实施负责人一人、没有修改或联合的其他仓库、也没有跨服务风险时，最终 `verify` 不要求先发布实施交接：
它核对全部条件后在结果的 `close_note` 中给出一份收尾说明草稿，包含平实语言摘要和结构化记录
（业务验收的文件指纹、知识处置——改动的 `.tw` 条目或不需要的理由——以及已有的关闭授权）。收尾说明由实施负责人
写给自己（`creator` 与 `owner` 相同），`remaining` 为空，`verified` 引用业务验收。工具不发布它；
用户发布后，`start` 返回 `closed: true`，再次 `verify` 直接使用已发布的记录。其他情况仍须先发布
实施交接，`verify` 会说明原因。

所有协作读取和草稿都返回 `delivery: not-evaluated`；接手结果始终保留
`closable: false`。最终交付命令另行核对实际执行、代码审查、知识回写和当前平台。
交付检查须完整核对接续条件并在结束前重读平台，不能只读取验收链接或检查
`remaining` 是否为空。
