# 阶段流程

用户要求"走完整流程""按阶段推进"，或项目规则要求时才读取本文件。其他情况仍按
目标选择方法。CS 前提与[接入约定](matt-integration.md)相同，缺少时报告并停止。
阶段只管推进次序和停点，知识读写仍遵循 CS，验证仍遵循
[团队协作与交付](team-delivery.md)。命令中的 `$WF` 指 `python3 <技能目录>/scripts/workflow.py`。

## 唯一状态源

父 Issue 是唯一状态源。阶段、子任务清单和决策项记录在父 Issue 评论的
`team-workflow-stage` 块中，只追加、不修改；最新的有效记录就是当前状态。
需求正文不随阶段改动，因此推进阶段不会让已有交接或审查失效。设计文档、聊天和
CS 任务记录只引用 Issue，不复制进度。

```bash
$WF status --issue <父Issue>                               # 只读：阶段、等你决定的事、子任务、能否关闭
$WF stage-draft --issue <父Issue> --record <阶段输入.json>  # 生成下一条阶段评论草稿，不发布
```

阶段输入为 `{"stage","note","children"?,"decisions"?,"confirmation"?}`，`stage` 填要进入的阶段，
省略的字段沿用上一条记录。阶段输入和台账清单等手工输入放在被忽略的 `.team-workflow/` 下。
草稿的 `markdown` 按已有授权追加到父 Issue；发布后重新运行 `status` 核对。

还没有父 Issue 或无法访问 GitHub 时，把这一点作为缺口报告；方案草稿先保留在本地，
父 Issue 建立后从 S0 开始逐条发布阶段记录，不能补记为已经处在后面的阶段。

## 阶段

| 阶段 | 做什么 | 产出与位置 | 退出标准 |
| --- | --- | --- | --- |
| S0 资料校对 | CS `brief` 读一次；核对需求、原型、代码现状 | 差异清单写入父 Issue 评论 | 差异有证据，未覆盖范围已列出 |
| S1 方案草稿 | [规格](../../matt-to-spec/SKILL.md) | 父 Issue 正文为规格；决策项写入阶段记录 | 每个待确认点都写成决策项 |
| G1 方案评审 | **停下**，等用户逐条答复 | 决策项状态、用户确认引用 | 用户确认；未关联子任务的决策全部确认 |
| S2 拆任务 | [任务拆分](../../matt-to-tickets/SKILL.md) | 子 Issue 各带 `team-workflow-task` 块；阶段记录写 `children` | 每个子任务都有验收、检查和所属仓库 |
| S3 实现 | [实现](../../matt-implement/SKILL.md)、[测试](../../matt-tdd/SKILL.md) | 代码；子 Issue 上的进度和交接 | 子任务交接无剩余工作和问题 |
| G2 逐任务验收 | [审查](../../matt-code-review/SKILL.md)、`verify` | 子 Issue 交接引用验证结果 | `status` 显示子任务可关闭，按授权关闭 |
| S4 汇总验收 | 跨仓时运行 `aggregate` | 父 Issue 评论 | 所有子任务已关闭 |
| G3 关闭 | **停下**，等用户确认关闭 | 阶段记录的确认引用 | 用户确认；决策全部确认 |

阶段只能前进一步，可以回退到任意阶段修改方案。离开 G1、G3 必须在 `confirmation`
中写明用户确认所在的评论链接或原话，代理不能代替用户确认。小任务可以连续推进，
但仍逐条记录阶段。

## 决策项

方案中所有需要产品、负责人或用户拍板的问题都写成决策项，不藏在文档末尾：

```json
{"id":"R-01","question":"断开归属店铺时是否阻断","options":["阻断","允许并进入未解析"],
 "recommended":"允许并进入未解析","default_if_unconfirmed":"保持现有实现，不改代码",
 "affects":["https://github.com/o/r/issues/12","A3"],"status":"pending"}
```

`affects` 填受影响的子 Issue 链接或验收 ID。确认后把 `status` 改为 `confirmed`，并在
`answer` 中写结论。用户在 Issue 中按编号答复选项即可。

- 未关联子任务的待定决策阻塞整个方案，不能离开 G1。
- 已关联子任务的待定决策只阻塞对应子任务；这些子任务不能实现，也不能关闭。
- 关闭父任务前，所有决策都必须确认。

## 硬暂停

即使在 S3 中途，遇到下列任一情况也要先停下，向用户说明影响并等待确认：

- 修改 proto、公开 API、跨服务契约或其生成代码；
- 跨仓重新生成代码；
- 修改数据库结构；
- 修改鉴权或可见范围口径；
- 实现需要回答一个尚未确认的决策项，或在多种口径中选一种。

## 子代理与中断恢复

多代理不是必需的。确实需要并行时，并发不超过 2 个，启动前说明目的和预计额度。
启动前先写台账，输出写到台账给出的路径，不要写到 `/tmp`：

```bash
$WF agents --ledger <名称> --plan <清单.json>          # 清单 [{"id","purpose"}]
$WF agents --ledger <名称> --mark <id> --status running
$WF agents --ledger <名称> --mark <id> --status completed   # 输出文件已写入后
$WF agents --ledger <名称>                             # 继续工作前先读
```

状态取值：`planned`、`running`、`completed`、`failed`、`interrupted`、`degraded`。每次变更
都保留在该项的 `history` 中；中断后由当前代理补做完成的项目出现在 `recovered` 中，
汇报时仍要说明它曾经中断、改为串行补做。说明预计额度时，写出代理数量和每个代理
要读取的大致范围（例如"2 个代理，各读一份 PRD 和对应模块"）。

用户说"继续"或会话恢复时，先读台账：

- `reuse` 中的结果直接读取，**不得重启**；
- `recover_serially` 中的项目由当前代理串行补做，或询问用户，**不得自动再次并发启动**；
- 失败、中断都要写 `--reason`；改用抽查替代时标记 `degraded`，并在原因中写明未覆盖的范围。

降级结果在汇报中单列，不能写成"已完成"或"核对完成"。子代理的结论要先核对源码，
核实后才能写入方案或审查结论，并且只引用已核实的条目。

## 汇报

阶段流程中，每轮回复的第一行固定为下面的格式，其中阶段写当前所处或停留的阶段；产出方案后停下等评审时写 G1：

```text
阶段 S3｜下一步：实现子任务 #12｜等你决定：R-08（是否阻断断开归属店铺）
```

阶段结束或最终汇报按以下顺序：

1. 需要你决定的事
2. 可关闭的项
3. 阻塞项
4. 已完成内容和证据（验证结果路径、交接链接）
5. 降级与未覆盖的范围

## CS 时机

- S0 读一次 `brief`；之后只有新代理、上下文丢失或范围变化时补读。
- S1–S3 不写 CS。必须中断或交接时，只写空 `items` 的 `in-progress`/`partial`/`blocked` 记录。
- 方案或审计已产出但未通过 G1，不是 `completed`。
- S4 通过后写一次 `completed` 记录，必要时新增卡片。
