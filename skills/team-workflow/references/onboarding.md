# 接入、升级与回退

先读取项目规则和真实验证入口，再从发行包 examples 选择接近的配置。命令、环境和风险覆盖必须对照当前代码确认，不把示例当已通过证据。

项目只增加 `.team-workflow.json` 和一条指向本技能的入口说明；将运行产物目录 `.team-workflow/` 放入项目忽略规则。业务测试继续属于业务仓库，通用工具从插件发行目录运行。跨仓知识权威入口仍由项目维护。

读取当前安装的 CS 技能，执行其只读预检。未初始化按 CS 的当前流程建立知识；格式过旧时报告重建需求，普通升级不得清空 `.codestable`。所有项目使用外置 CS，不复制其脚本。

## 升级第一版

```bash
python3 <技能目录>/scripts/workflow.py migrate --root <项目> --profile .team-workflow.json
```

输出配置建议和需要复核的项，不写项目。显式 `--out .team-workflow/migration.json` 可以保存建议。核对后采用其中的 `profile` 对象。迁移保留命令，把代码默认检查与文档检查分开；结果格式默认 `command`，需要人工选择 Go/JUnit 格式、必要用例及环境。运行旧材料核查时使用原配置和 `check.py`，其语义保持不变。

## 团队分发

工作流插件版本、项目配置格式、CS 能力分别记录。本版插件 0.4.0-rc.1，继续读取项目配置格式 2 和原有第二版材料，新增协作与可移植结果格式 3。验证使用的 CS 基线为 2.1.0 / Wiki 格式 4；其他版本需通过预检与相同契约测试才可推广。在途任务保留其记录的发行版本，不自动切换。

先由维护者发布候选包，在代表项目试用后统一团队采用的发行版本。安装遵循宿主支持的插件流程；源目录更新不等于每位成员的缓存已更新。通过 `workflow.py version` 与 `project` 输出核对实际工具和 CS。

普通兼容版本更新不修改各项目配置。不兼容变更明确拒绝并给出迁移步骤。保留上一发行包及配置原版本以便回退；回退不清空 CS，无法读取的格式不静默降级。不要把新版配置交给旧检查程序后忽略失败。

发布工具 `scripts/package.py` 只构建本地 ZIP，排除任务证据、知识、缓存和仓库元数据。本仓库没有配置远端分发地址；远端建仓、成员安装和团队版本推广分别保留可核查状态，不把 ZIP 生成等同于已推广。

## 统一文档入口

使用独立 CS 2.1.0。将现有 GLOSSARY、ADR 与项目规则登记到 CS `wiki.documents`；
跨仓路径复用 `wiki.repositories`。参见 CS 的 `references/documents.md`。新登记只写
来源、范围和状态，不复制正文。修改 AGENTS 的相关入口指向 CS brief，不建立第二套
词汇或决策库。保留项目原有业务约束与直接文档导航链接。

已重复的卡片逐项对照原文：完全覆盖则用 reference+supersedes 保留旧正文为历史；
部分覆盖则只保留独立经验；真实冲突先报告并解决，不能批量宣布“已同步”。
技能升级不重建 `.codestable`。
