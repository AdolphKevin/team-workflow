# 分节方案与逐节批准

方案分节批准、按依赖计算变化；业务字段见[工具约定](contracts.md)，执行与场景证据见[业务验收术语](business-acceptance.md#1-术语)。

## 内容与依赖

方案分为范围、接口、数据、验收和实施任务。任务关联验收与修改范围，完整业务验收列在全局范围；前置任务提供业务验收记录。

任务的 `scope` 是仓库相对路径前缀：路径本身及下级均在范围内，`.` 表示整个仓库。与任务 `paths` 共用规范化：折叠 `./` 段、重复斜杠和结尾 `/`；绝对路径、`..`、反斜杠、NUL 和通配符报错。比较时规范化，保留入库原文；简报把 `.`、已存在的目录和以 `/` 结尾的路径按目录读取；`.` 表示整个仓库，只按任务文字、标签和符号选条目。

父方案和子任务分别评估复杂度、风险、工作量、依据、未决事项与所需能力，任务节评估覆盖方案评估。任务按评估结果归类，缺少评估时报告缺口。批准路径为：

- 简单任务：短方案 → 实施 → 场景验收 → 合并评审，评审人同时批准方案与代码。
- 中等、复杂任务：方案获具名批准 → 实施 → 场景验收 → 评审。

风险决定必要检查集合。中等、复杂任务将方案原文放入草稿变更请求，获批后实施；发布步骤见[发布与隐藏记录](#发布与隐藏记录)。

记录及章节指纹的覆盖内容见[记录绑定](contracts.md#记录绑定)。

## 批准与变化

批准记录姓名、版本、章节及可选确认依据，覆盖实际确认的内容；新增或修改要求、暂缓事项重新确认。

`approval-draft` 的方案模式默认选本任务所需章节及依赖中待批准的部分，加待确认删除（`deletion_ids`）；合并模式选全部所需章节、依赖与相关删除。方案无待批内容或合并批准已覆盖当前全部内容时返回“没有需要批准的章节”。`--sections A3,T2` 指定编号，`--sections all` 选全部当前章节；显式编号纳入这些编号尚待确认的删除。`--record` 接受 `section_ids`、`deletion_ids`，可读批准按文档顺序列“编号 标题”。

变更请求描述展示方案原文，记录与批准追加评论，由项目脚本读取。可选 `revision` 的记录及本地提交核对见[批准命令](contracts.md#实施批准与代码评审)。

评审 Markdown 含完整绑定区，可发布到变更请求，用 `review --task <身份> --from-platform` 导入；`deliver` 按平台和本地评审时间采用较新者。逐项复核、来源核对及问题历史见[工具约定](contracts.md#变化后逐项复核)。

变化影响按前后依赖图的并集计算，删除依赖也保留原受影响范围。增删章节、业务约束或评估时重审对应部分；完整历史从修订 1 连续提供，保留删除与已知问题的处置。

## 状态与接口

| 输出 | 含义 |
| --- | --- |
| `implementation_ready` | 选中工作已有有效方案、评估和指派；中等及复杂任务另有适用批准；相关实施问题和前置任务已解决 |
| `fully_approved` | 选中章节和相关删除已有有效批准 |
| `local_review_valid` | 批准与实际修改归属可核对；简单任务另有当前合并评审 |
| `acceptance_ready` | 评审与相关问题处置齐备；业务结果由 `accept` 核对 |

局部核对用 `section_ids`，自动纳入上游；`history` 保存完整历史，`changed_paths=None` 表示未知，空列表表示已核实无变更。

## Markdown 原文格式

方案正文维护为仓库中的 Markdown，起点见[方案模板](../templates/design.md)。显式 `--design`、方案 `--record` 和 `--design-history` 均读取此格式；`.tw/local/` 中的 JSON 快照用于工具内部引用。

文件第一行是 `---`，结束的 `---` 之间每行一个 `字段: JSON值`，字段齐全且唯一：

| 文件头 | 内部字段 | 取值 |
| --- | --- | --- |
| `design` | `id` | 稳定方案编号，字符串 |
| `task` | `task_id` | 所属任务编号或规范地址，字符串 |
| `revision` | `revision` | 正整数，每次发布加一 |
| `assessment` | `assessment` | `complexity` 取 `simple`、`medium`、`complex`；另含 `risks`、`effort`、`drivers`、`uncertainties`、`required_skills` |
| `roles` | `roles` | `design_owner`、`implementation_owner`、`acceptance_owner` |
| 自动补齐 | `data_version`、`kind` | 固定为 `1`、`design` |

评估和业务字段见[场景与证据](contracts.md#场景与证据)。

```markdown
## 接口约定
<!-- tw-section id=api type=interface depends=scope-global -->
实际接口行为与限制。
```

| 章节写法 | 内部字段 |
| --- | --- |
| 标题文字（`#` 至 `######`） | `title` |
| 标题下一行的 `tw-section` 注释 | `id`、`type`、`depends_on`；`depends` 可省略，多项用逗号 |
| 标记下一行至下个同级或更高级的带标记标题 | `body`；未标记子标题、代码示例仍属正文 |
| 首个标记标题之前的文字 | 章节外说明，可写标题、状态、批准记录 |

`type` 为 `global-scope`、`scope`、`interface`、`data`、`acceptance`、`task`；全局节恰好一个，写 `id=scope-global type=global-scope`。代码围栏外的标记生效。

### 结构化章节字段对照

标签行位于正文之后，写 `- 标签：值`，以下路径均相对本节 `data`。单值标签取到行尾，分号、顿号、字面引号原样保留。多值标签用 `、` 分隔，空数组写 `无`；操作用 `；` 分隔。某项含实际分隔符时，用 JSON 引号包住该项；依据保护 `；` 和 ` / `，验证列表保护 `、` 和 `；`。

换行及特殊边界用 HTML 字符实体保存：`&`、列表项首尾空白、未闭合的起始引号、起始 `[`、字面值 `无` 均转义，读取时还原；普通行内空白、括号和引号保持原样。数组可直接写 JSON 数组，表格单值列按下方缺省标记和实体规则书写。

| 类型 | 标签或表列 | 内部字段 |
| --- | --- | --- |
| 全局范围 | 需求级验收 | `requirement_acceptance` |
| 全局范围 | 影响范围表：仓库、入口、操作、产生方、使用方、提交负责方、验收 | `impact[].repository/entrypoint/operations/producer/consumer/commit_owner/acceptance` |
| 验收 | 场景 | `scenarios[]`：`<仓内路径>#<节点编号>`，同文件多节点用 `、` 分隔；读取后补 `sha256` |
| 验收 | 依据 | `sources[]`：`位置 <ref>；版本 <version>；确认人 <confirmed_by>`；多项用 ` / ` |
| 验收 | 检查 | `checks` |
| 验收 | 验证 | `verification`，见下表 |
| 任务 | 验收、范围、前置任务 | `acceptance/scope/blocked_by` |
| 任务 | 评估（可选，JSON 对象） | `assessment`，字段与文件头一致 |
| 各类型的其他数据 | `数据 "<字段名>"`，值为 JSON | 保存扩展字段 |

依据也可写 `<ref>（<version>，<confirmed_by> 确认）`，扩展字段名按 JSON 转义，特殊字符可用 Unicode 转义。场景引用和来源要求见[场景与证据](contracts.md#场景与证据)。

检查非空时，验证标签写在一行：

```markdown
- 场景：docs/sop/<批次>.yaml#SOP-02、SOP-03
- 验证：自动；用例 Arithmetic::adds；替身 项目平台脚本夹具
```

| 验证中的文字 | `verification` 内部字段 |
| --- | --- |
| 自动 | `method`: `automatic` |
| 用例（可选） | `cases` 数组，省略为空数组 |
| 替身（可选） | `substitutes` 数组，方案允许的替代依赖，省略为空数组 |

检查为 `无` 时省略验证标签；逐场景人工执行及检查覆盖声明见[场景与证据](contracts.md#场景与证据)，评审用例的补充规则见[实施、批准与代码评审](contracts.md#实施批准与代码评审)。

影响范围表使用上述七列与 Markdown 分隔行，每行对应一项调查。已知问题用独立标题及下一行 `<!-- tw-issues -->`；无问题时可省略标题和表格。

| 已知问题表列 | 内部字段 |
| --- | --- |
| 编号、问题、负责人、影响章节、阻塞阶段、状态 | `issues[].id/summary/owner/affects/blocks/state` |
| 原因、证据、确认人、确认依据、后续任务、范围调整 | `issues[].resolution.reason/evidence/confirmed_by/confirmation/follow_up/scope_change` |

保留全部列；缺省处置字段写 `—`，空字符串写 `""`，空数组写 `无`。表格和标题的 `|`、换行、`&` 用 HTML 字符实体转义；读取后还原，保留标签、字段和数组顺序。

正文统一为 LF，去掉首尾空行与行尾空白，保留行内空格、段落间空行、代码围栏和缩进。`render` 在带标记标题前、正文与首个标签间、标签与表格间各输出一个空行；`load` 将这些排版空行与正文分开。`load(render(design))` 返回规范化正文和原值字段。正文的保留标签、标记行可加 Markdown 反斜杠转义，读取后还原；渲染器转义未闭合的代码围栏。缺文件头字段、缺标签、非法值、重复编号、未知类型或引用缺失均报原文行号。

## 发布与隐藏记录

先提交方案文件，完成任务正文和变更请求描述等编辑；最后运行 `design-draft --issue <地址> --record <方案.md>` 并立即发布记录，保留此前评论。历史变化时错误列疑似改动地址，无匹配则提示可能删除或插入评论；核对后重新生成。

`pr_description` 展示原文及“本方案引用的检查”表，取自同一提交的 `.tw/config.json`，缺配置或检查时省略；`markdown` 为发布评论。记录的 `design` 含 `id`、`revision`、`repository`、`path`、`commit`、`sha256` 六个字段；外层保存任务、发布者、要求签名、历史摘要及前序引用。

工具按本机仓库映射，以 `git show <commit>:<path>` 读原文，核对摘要与身份后解析；缺提交先获取提交，缺映射先补映射。`status`、`start` 提示变更请求描述与最新原文的展示差异。相对链接按原文目录与发布提交改写：配置 `file-url` 时用其地址并保留片段，其余显示文字与路径；越界路径转纯文本，代码、绝对链接、页内锚点原样保留。

平台的任务、方案、批准、交接（含收尾）、进度均用可读 Markdown 加 `<!-- tw-record {...} -->`。可见部分展示目标、验收、负责人、章节和状态等，工具从 `tw-record` 解析数据；评审绑定区采用相同注释。受保护区核对、逐项复核和平台导入见[工具约定](contracts.md#实施批准与代码评审)。注释内 JSON 字符串将 `-`、`<`、`>` 编为 Unicode 转义，换行用 JSON 转义，确保注释完整，读取后逐字还原。

方案文件采用当前验证格式；读取失败时改写并提交原文，用 `design-draft --issue <地址> --record <方案.md> --reconcile "<原因>"` 从第 1 版重启，此前批准作废并重新批准。`approval-draft --issue <地址> --reconcile "<原因>"` 对账批准冲突；两者绑定当前历史摘要。
