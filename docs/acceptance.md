# 验收标准

| 范围 | 可观察的通过条件 |
| --- | --- |
| 两条流程 | 简单任务可先实现并合并评审；中等、复杂任务未获具体评审人确认不能实施；所有风险仍完成对应检查 |
| 分别评估 | 父方案和拆分任务分别记录复杂度、风险及依据；简单子任务不被父方案复杂度覆盖 |
| 逐节重审 | 接口变化只影响相关验收与任务，全局约束变化影响全部；增删章节、删依赖及确认业务选择不能错误复用旧批准 |
| 历史保留 | 后续版本仍能发现未确认删除；其他格式、旧算法或缺失历史不能被当作完成证明 |
| 独立任务 | 一条分支待评审时，无关分支可以继续；未知变更归属不能报告局部评审有效 |
| 接力实施 | A 的方案由 B 在新会话接手；B 仅凭共享材料获得范围、批准、职责、知识和验收要求，不重复请求已批准的开工确认 |
| 简单任务 | 无子任务仍可完成；不强制逐阶段评论或固定评审职级；高风险的简单任务保留合并评审路径 |
| 验证复用 | 五个任务共需七项检查时，每项执行一次；只改动或提交 `.tw` 知识不使按内容绑定的检查过期；相关输入变化必须重新核查 |
| 真实结果 | 失败、零用例、必要用例跳过、缺少原始报告、错误前端检查或无法确认环境不能通过；运行期间源码变化不能通过 |
| 跨仓范围 | 构建依赖不被误判为协作交付；真正修改及联合验收完整覆盖；证据不依赖个人绝对路径 |
| 平台核查 | Issue 任务漏传 `--issue` 仍核查平台；链接可访问、子任务关闭或剩余文字为空不能替代验证；未确认进度与冲突阻止最终交付 |
| 知识顺序 | 保留开工简报；业务验收先通过，再在同一改动中更新 `.tw` 知识；交付报告写明改动的条目或不需要的理由，`tw check` 没有错误 |
| 知识读取 | `tw brief` 按路径、符号、标签和词组选出现行约束、决策与教训，篇幅不超过预算；命中“放弃过的做法”时主动提醒；查询与检查零写入 |
| 知识检查 | 占位内容、失效的 scope 与守护测试、缺少原因的放弃记录、未忽略或被跟踪的 `.tw/local/`、残留的旧目录都被报告 |
| 迁移 | 代理按迁移指南把旧知识逐条核实后改写，未核实的内容列入迁移说明，用户在 PR 中确认，撤销 PR 即可回退 |
| 清理与更新 | 在途任务、历史批准及被引用证据不被删除；非当前格式的配置或记录被明确拒绝；项目要求更新的工具时提示更新；错误能指出具体缺口和下一步 |
| 来源与安装 | 15 个 MATT 技能、41 份上游资源和许可可追溯；反向补丁逐文件一致；模板随技能安装，通用脚本不复制进业务仓 |
| 标准发现与记录 | 从技能、分发指引和日常交付或每周复盘入口能找到同一份[业务验收与质量改进标准](../skills/team-workflow/references/business-acceptance.md)，能用三份模板记录真实输入、结果与证据 |
| 首次验收与回归 | 试用者能安排未参与实现的测试同事、用户或 AI 独立验收，再按业务保证选择单元、集成或 E2E；不会要求所有回归都启动完整业务链路 |
| 缺陷保护 | 试用者能识别仅在修复版通过但未证明原问题检出能力的用例；旧版或受控恢复原失效机制的失败证据与修复版通过证据明确对应 |
| 完整链路 | “成员收到提醒”的场景中，试用者能区分发送记录与实际成员连接收件，写清 E2E 起终点、关键环节、替代依赖及未覆盖范围 |
| 持续运行 | 试用材料能追踪本机与 CI 各自的依赖就绪、隔离数据、重复执行、失败证据和清理结果；未执行的环境保持未验证，装配变化有对应维护项 |
| 结论边界 | 人工独立验收通过、自动回归待完成与整体交付状态分别呈现；不会从部分场景通过推断场景穷尽或程序无缺陷 |
| 项目验收方式设计 | 在两类不同项目中，试用者从代码和配置调查入口、存储、消息通道、已有测试与 CI 并注明来源，列出关键业务保证及层次和观察点，复用项目已有框架，产出项目验收方案；查不到的事实写未知，不照搬其他项目的工具或命令，方案未经开发与测试确认时保持草稿 |
| 业务来源与独立性 | 验收场景记录 SOP 或需求原文的位置、版本和确认人，缺少时 `start` 提示、`accept`/`deliver` 拒绝；实施者意见可以保存，作为独立评审或人工观察证据时验收仍拒绝，并说明工具无法识别同一人的不同名称 |
| 过渡状态 | 在没有集成或 E2E 入口的项目中，试用者保留独立人工验收证据，整体交付写为“人工验收通过，自动回归未完成（待建设）”，登记含负责人、期限和确认人的建设任务；不降低回归层次，不写成完成 |
| 入口建设与工具状态 | 首条新建入口有干净运行、重复运行、故意失败和 CI 实跑四项证据；`verify` 对待建设条目显示 `regression_pending` 并逐条列出，`delivery_complete` 含义不变 |
| 缺陷关联与周复盘 | 开发与测试能分别记录违反要求、影响需求、引入改动和当时应发现的场景，保留未知及调查依据；每周按实际结果落实改进、责任人、期限和后续效果，不按发现时间归责或以数量和通过率主导质量判断 |

工程验证执行完整回归、发行和 MATT 来源校验，覆盖 Python 3.10 与 3.13。执行受环境限制时记录具体项目及原因，不能跳过后写成通过。

技能变化在隔离目录交给独立代理，用真实原始请求验证选择流程、读取材料、批准复用及最终报告，检查实际输入与结果。代理试用用于发现使用问题，不能代替真实团队条件。

真实试点继续采用 LiveChat Core→Gateway 频道授权链路：使用真实 Core 接口、Gateway 订阅入口与测试数据库，核对合法订阅、越权拒绝、权限变化后的再授权，以及 Core 不可用时拒绝新的授权。记录 Core、Gateway、common 的真实版本和未提交变化，业务原始材料留在其项目权限范围内。

正式推广要求两位真实成员分别使用 Codex、Cursor，在不读旧聊天、不接受口头补充时双向接续任务；下一次相关工作能找到并正确使用先前知识。单个操作者或两个代理不能替代两位成员。未满足时仅保留候选版，并明确试点缺口；实际执行结果写入[验证记录](validation.md)。


工具额外验收：缺场景或评估不能开工；父需求不能用子任务结果代替完整业务验收；单元检查
不能证明未经过的业务入口，替代依赖不能超出声明；评审问题不能在重试或交接中消失；知识
完成必须绑定实际业务验收且范围相关；非当前格式的记录被拒绝；隔离未解决的
检查不执行；原始材料缺失不能接续交付。纯文档允许明确的人工观察，不编造运行用例。
