# 0.6 验收标准

| 范围 | 可观察的通过条件 |
| --- | --- |
| 两条流程 | 简单任务可先实现并合并评审；中等、复杂任务未获具体评审人确认不能实施；所有风险仍完成对应检查 |
| 分别评估 | 父方案和拆分任务分别记录复杂度、风险及依据；简单子任务不被父方案复杂度覆盖 |
| 逐节重审 | 接口变化只影响相关验收与任务，全局约束变化影响全部；增删章节、删依赖及确认业务选择不能错误复用旧批准 |
| 历史保留 | 后续版本仍能发现未确认删除；旧格式、旧算法或缺失历史不能静默转换成新版完成证明 |
| 独立任务 | 一条分支待评审时，无关分支可以继续；未知变更归属不能报告局部评审有效 |
| 接力实施 | A 的方案由 B 在新会话接手；B 仅凭共享材料获得范围、批准、职责、知识和验收要求，不重复请求已批准的开工确认 |
| 简单任务 | 无子任务仍可完成；不强制逐阶段评论或固定评审职级；高风险的简单任务保留合并评审路径 |
| 验证复用 | 五个任务共需七项检查时，每项执行一次；仅新增、暂存或提交 CS 记录不触发业务重跑；相关输入变化必须重新核查 |
| 真实结果 | 失败、零用例、必要用例跳过、缺少原始报告、错误前端检查或无法确认环境不能通过；运行期间源码变化不能通过 |
| 跨仓范围 | 构建依赖不被误判为协作交付；真正修改及联合验收完整覆盖；证据不依赖个人绝对路径 |
| 平台核查 | Issue 任务漏传 `--issue` 仍核查平台；链接可访问、子任务关闭或剩余文字为空不能替代验证；未确认进度与冲突阻止最终交付 |
| 知识顺序 | 保留开工简报；业务验收先通过，再完成 CS 记录和知识核对；简报事后补读如实报告 |
| CS 关联 | 外部任务引用经创建、更新、整理和精确查询保持准确，多候选不自动合并；不依赖正文子串 |
| CS 计划 | 旧计划文件明确报错且不变，并发同名导出只能一个成功；失败后不会继续应用旧计划；成功响应丢失可按原请求重试 |
| CS 提示 | 当前知识的来源变化始终可见；无关和重复维护提示折叠；查询及回执核对零写入 |
| 清理与升级 | 在途任务、历史批准及被引用证据不被删除；旧任务不静默升级；错误能指出具体缺口和下一步 |
| 来源与安装 | 15 个 MATT 技能、41 份上游资源和许可可追溯；反向补丁逐文件一致；模板随技能安装，通用脚本不复制进业务仓 |

工程验证执行完整回归、发行和 MATT 来源校验，并针对 CS 远端默认分支运行真实接口及并行组合测试，覆盖 Python 3.10 与 3.13。执行受环境限制时记录具体项目及原因，不能跳过后写成通过。

技能变化在隔离目录交给独立代理，用真实原始请求验证选择流程、读取材料、批准复用及最终报告，检查实际输入与结果。代理试用用于发现使用问题，不能代替真实团队条件。

真实试点继续采用 LiveChat Core→Gateway 频道授权链路：使用真实 Core 接口、Gateway 订阅入口与测试数据库，核对合法订阅、越权拒绝、权限变化后的再授权，以及 Core 不可用时拒绝新的授权。记录 Core、Gateway、common 的真实版本和未提交变化，业务原始材料留在其项目权限范围内。

正式推广要求两位真实成员分别使用 Codex、Cursor，在不读旧聊天、不接受口头补充时双向接续任务；下一次相关工作能找到并正确使用先前知识。单个操作者或两个代理不能替代两位成员。未满足时仅保留候选版，并明确试点缺口；实际执行结果写入[验证记录](validation.md)。
