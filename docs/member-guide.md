# 成员操作说明：项目知识

项目知识存放在各仓库的 `.tw/` 目录，与代码一起评审。代理按 `team-knowledge` 技能读写知识；这份说明面向团队成员，介绍你会看到什么、需要确认什么。

## 你会看到的文件

| 位置 | 内容 |
| --- | --- |
| `.tw/overview.md` | 项目做什么、和谁协作、从哪里开始读代码 |
| `.tw/glossary.md` | 项目特有的术语，以及应避免的同义词 |
| `.tw/rules/` | 现在必须保持的行为和契约，写明业务来源与例外 |
| `.tw/decisions/` | 难以逆转的决策：背景、备选、后果、放弃过的做法 |
| `.tw/lessons/` | 踩过的坑：现象、根因、修复与防护、发现方法 |
| `.tw/local/` | 只在本机，不提交 |

条目存在就表示它现在有效。决定改变时，正文改写为新结论，旧做法和放弃原因保留在“放弃过的做法”中；完整的修改过程查 git 历史。

## 本机材料与清理

`.tw/local/` 按检出目录隔离，被 Git 忽略。各处用途如下：

| 位置（位于 `.tw/local/` 下） | 用途 |
| --- | --- |
| `tasks/` | 每项任务的上下文、方案与批准副本、检查输出、评审及交付材料 |
| `batches/` | 批次操作的材料 |
| `imports/` | 导入的材料与结果 |
| `validation-active/` | 正在验证的进程标记，防止清理使用中的材料 |
| `agents/` | 代理分工与进度台账 |
| `cache/` | 可重新生成的知识查询缓存 |
| `repositories.json` | 这个检出目录的共享仓与外部文件路径覆盖 |
| `.maintenance-lock` | 清理操作的互斥标记 |

整目录删除后，进行中任务需要重走流程；没有 Issue 的离线任务，其方案和批准无法从平台找回，只能依靠本机备份恢复；已交付任务也会失去原始证据。检出目录内的映射覆盖会丢失，缓存可以重建。

`git clean -fdx` 同样会删除 `.tw/local/`。清理构建产物时，可用保留忽略文件的 `git clean -fd`，或用 `git clean -fdx -e .tw/local` 明确保留本机材料。

清理任务材料时，先用 `tw team cleanup --cleanup-scope all` 预览，把计划保存到仓库外，核对后再用 `tw team cleanup --apply --plan <计划文件>` 应用。`tw audit` 会列出不归工具管理的条目及大小。试点和手工输出应放在仓库外，例如系统临时目录。

共享仓默认路径放在 `${XDG_CONFIG_HOME:-~/.config}/tw/repositories.json`，按 `.tw/config.json` 的 `project.id` 分组：

```json
{"projects": {"github.com/acme/core": {"repositories": {"common": "~/src/common"}}}}
```

查找顺序为命令行 `--repository` > 检出目录的 `.tw/local/repositories.json` > 用户级文件，按别名逐项覆盖；`inputs` 中的外部文件路径同样逐项合并。两个文件由成员或代理编辑，工具只读。已有项目可以继续只用检出目录的文件；缺少路径时按提示配置，工具不会猜测或自动克隆。

任务只要对别人重要，就开 Issue。方案、批准、交接和交付结论以草稿形式发布到 Issue 或变更请求，方便本机材料丢失后找回。

## 日常

- 开工前，代理用 `tw brief` 读取相关知识。brief 里出现“曾放弃的方向”时，不要在没有新理由的情况下重新采用。
- 完成后，代理在同一个 PR 中更新知识。下面三种情况必须写：
  - 修复了根因不明显的缺陷：写 lesson，尽量附守护测试；
  - 做了难以逆转的选择：写 decision；
  - 改变了必须保持的行为：写 rule。
- 没有可复用的结论时可以不写，但交付说明里要写明理由。

## 评审知识改动

团队任务先用 `tw team start --task <任务文件> --design <方案>` 开工；之后用 `--task <身份>`（本地任务编号或完整 Issue 地址）运行、查看状态、生成草稿、验收和交付。工具在任务目录的 `current.json` 记录材料路径和指纹，输入相同的 `start` 接续，输入变化则新建上下文并清空后续材料。本地验收项可只写编号，由方案补全；平台任务仍须写全。

简单任务的日常流程为 `start → run → review --submit → deliver --reason <理由>`。中等、复杂任务先由具名评审人批准方案，可用 `approval-draft --reviewer <姓名> --mode plan` 生成批准记录，再开工。run 在必需检查全部通过后自动给出 review.md。

未参与实施的评审人填写姓名、知识冲突处理、规范和需求及各验收项的通过/不通过与理由、问题处置。简单任务需合并批准时填写“批准方案与代码：是”。人工观察的观察人、时间、操作、结果、数据和证据由人填写；绑定区和自动结果不改，路径及指纹由工具生成。

完整的“不通过”评审也能提交并保存问题，accept/deliver 会逐项列出不通过项和阻塞问题，仍不能交付。格式错误或过期绑定按行号、小节提示修正。源码、方案、检查策略或选中运行变化后，工具保留旧稿、预填意见；先读“变化”，逐项把“待复核”改为“已复核”再提交。已知问题身份保持不变，处置可以更新。

要改知识时，提交后先 `accept --task <身份>`；通过后更新知识并运行 `tw check`，再 `deliver --task <身份>`。无知识改动时给 --reason 即可。显式 `--context`、`--run`、`--review`、`--report` 等路径保留，也可用 `review --submit --file <路径>` 提交别处的 Markdown。

`status --task <身份>` 列出当前有效的验收和交付记录、过期步骤与下一条命令。最终交付完成后，关闭 Issue 还需收尾说明或交接已发布，以及报告中的具名关闭授权；工具不执行关闭。详见[交付与关闭](../skills/team-workflow/references/team-delivery.md)。

除了照常看代码，再检查以下几点：

1. 结论是否与代码和业务要求一致。工具只做结构检查，不判断结论对不对。
2. 是否记录了一次性结果、测试计数、工具版本、行号或任务过程。这些都不该写进知识。
3. 决策改变时，旧做法是否已移入“放弃过的做法”，并写明原因。
4. 跨服务的约定是否只写在契约提供方的仓库，其他仓是否用 `related` 引用。
5. `tw check` 没有错误。

## 迁移已有项目

旧的 `.codestable/` 由代理按迁移指南整理，不使用脚本。你需要做三件事：

- 在迁移 PR 中逐条确认业务规则和决策；
- 查看“未核实、没有迁入”的清单；
- 决定未跟踪的旧证据是否删除。

如果迁移结果不对，撤销 PR 即可回退。

## 找回历史教训

这不是默认步骤。需要时，直接要求代理“从历史中找回某方面的教训”，确认候选后再写入。
