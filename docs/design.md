# 设计边界

本仓维护团队流程和直接复用的 MATT 方法；CS 独立提供知识读取与写入。通用工具仅使用 Python 3.10+ 标准库，业务测试和环境准备留在业务仓库。

## 入口与职责

从 `team-workflow` 开始的新任务默认使用第四版团队流程。独立 MATT 调用保持轻量；进入团队流程后切换方法，仍保留该任务的批准、验收及交接要求。任务平台维护进行中的工作，CS 保存最终紧凑结果和独立经验；术语、规则与设计决策始终由登记的原文拥有正文。

任务评估分别描述复杂度、业务风险、工作量、依据、未确定事项与所需能力。父方案和拆分任务分别评估；任务节可以用自己的 `data.assessment`，未填写时继承方案评估。简单子任务不会仅因父方案复杂而被迫采用事前评审。

简单任务可以实现后合并评审方案与代码，所有风险类型均适用；风险决定必要检查。中等、复杂任务先由具体评审人确认方案。评审人不设固定职级或强制独立性，职责允许兼任。已有明确批准和指派可以直接接续，已批准范围内的接口、数据库、权限修改不增加重复暂停。

## 方案与协作

方案按稳定编号分节，保存完整历史。批准绑定明确章节及其依赖内容；新增、删除、依赖调整或实质变化按旧新关系计算影响，未受影响的批准可以继续使用。算法和格式由[分节方案约定](../skills/team-workflow/references/designs.md)维护，不在其他文档复制。

方案交接与实施交接分别记录。接手材料必须包含当前需求、评估、有效方案与批准、职责、验收方式、知识入口、依赖、自主决定范围、问题责任和下一步，使接手者无需旧聊天即可工作。简单任务可以只用一条任务，不强制子任务或逐阶段评论。

GitHub 读取器只做读取操作，写入命令仅生成草稿。发布前沿用已有授权核对平台最新状态；并行冲突、被改写历史和未纳入交接的进度不能被“最新一条”掩盖。关闭任务另需已有明确授权，验证链接可访问不等于业务通过。

## 验证与知识边界

执行结果绑定实际源码、依赖内容、具体检查及环境；评审绑定任务要求、方案和代码；知识核对绑定 CS 记录和相关来源。暂存布局、无关流程配置或知识记录的提交不使业务检查失效；确实依赖提交编号的检查显式声明。多任务检查取并集，执行一次后分别核对验收覆盖。

检查环境声明为无可变外部状态，或由业务仓提供能确认夹具版本与必要数据状态的只读命令。并行开发使用独立目录与相应依赖配置；共享目录在验收期间停止编辑。运行期间源码或环境变化，结果不能通过。

构建依赖、实际修改仓库、联合验收服务分别声明。构建依赖仍参与内容记录，不自动产生协作成员或联合负责人。跨仓证据使用仓库身份、仓内位置与内容指纹，本机目录单独映射；复制日志不能替代原始执行证明。

知识顺序为：开工按真实范围读取，实施与业务验收，通过后使用 CS 写入最终记录，再核对知识和交付。保留开工简报，新增知识改变查询结果时追加收尾复核。CS 的 `task.external_refs` 关联外部任务；不再在自由文本中查找 Issue 链接。计划文件由 CS 保证独占创建，调用方在失败后停止，不能沿用旧计划。

CS 的当前知识核实提示与知识库维护事项分别展示。它保持只读查询，也不替工作流决定开发能否继续。本仓仅核对公开能力，不锁定 CS 的版本或提交。

## 兼容与发布

第四版是新任务默认格式。第二、三版材料保留原有含义；在途任务显式切换后才采用新规则。升级通用工具不重建知识库，不更新原有证据的版本标记来制造新版通过记录。工具模板随技能分发，实际命令统一见[第四版工具约定](../skills/team-workflow/references/contracts-v4.md)。

自动化测试、隔离代理试用和两位真实成员试点分别记录。未完成正式试点时保留候选版状态，不自动提交、外部发布或推广到成员安装。
