# 设计边界

本仓是基于 CS 的 MATT 方法包，另提供可选团队工具。使用开发技能前，CS 已安装且项目已完成知识初始化；主入口帮助选择方法，普通调用无需团队配置或交付材料。个人选择模型、工具、规划和实现方式。

项目规则、术语和决策只有一份登记原文，通过独立 CS 的 brief/documents 读取；已有经验从同一入口检索。任务平台维护进行中的需求、职责、进度与问题。CS 完成记录只保留紧凑结果、依据与独立经验，不复制规格、进度或原文。

MATT 方法直接复用锁定的源码、模板与配套资源。适配入口引用 CS 的知识规则，各方法不再维护自己的知识流程。CS 本身不增加任务调度、阶段或验收关卡。环境复盘负责代理工作环境建议，CS 使用分析负责工具实际表现的反馈，均按需进行。

用户或项目规则显式开启阶段流程时，团队工具额外提供阶段、确认关卡和关闭条件。父 Issue 评论中的阶段记录是唯一
状态源，只追加、不改需求正文；G1 方案评审和 G3 关闭由用户确认，代理只生成草稿。子代理台账保证中断后复用已完成
结果、不自动重新并发启动。未开启时行为不变。

项目约定或用户明确采用团队工具后，才启用下述协作与交付约定；已有工具接口和核验要求保持有效。

GitHub 读取器只执行 GET。交接工具生成草稿，现有授权决定是否发布。协作者普通进度按请求编号去重并独立追加，负责人交接明确引用已确认进度。交接形成带前序指纹的历史，真实冲突明确保留；需求指纹与进度分离。可接续与交付完成是两个不同结论。

本地执行继续支持第二版完整工作区绑定。第三版可移植结果在执行时记录仓库身份、提交、内容、检查定义、环境和原始报告；GitHub 适配器核对来源并重解码原始报告。远端成功或本地摘要不能单独证明业务验收。

跨仓任务可用不同编号，但关联同一总任务。可移植联合清单使用仓库标识和版本，调用方单独提供本机目录映射；联合运行必须覆盖所有参与仓及公共依赖。未共享改动、本机外部文件和缺失证据准确留下缺口。

版本升级不重建知识，不自动改变在途任务所用插件。旧项目配置明确拒绝且不自动转换；新字段、当前要求或来源核查缺失时不能伪装成新版完成证明。

共享配置格式 3 只保存团队规则、仓内相对路径和逻辑依赖，本地映射只保存资源位置。
生成材料以任务和请求分目录，通过不可覆盖的原子发布防止并发覆盖；完成请求可重试，
中断请求保留状态并要求新编号。原文登记使用 CS 的独立文件，源码并行使用独立检出目录。
CS 的 `receipt-check` 负责相关性校验，无关任务或缓存不使简报失效。CS 接口按能力检查，
验证提交是观察记录，不是依赖锁定；不再通过整个 Wiki 或 CS 源码哈希判断材料有效性。
