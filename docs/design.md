# 设计边界

本仓维护团队流程、项目知识和直接复用的 MATT 方法，只有一个 Python 标准库运行时（`team-knowledge/scripts/tw_runtime`）。业务测试和环境准备留在业务仓库。合并重构的完整方案见 [proposals/2026-10-14-unified-redesign.md](proposals/2026-10-14-unified-redesign.md)。

## 入口与职责

`team-workflow` 是团队任务入口；`team-knowledge` 负责知识的读取、检查和迁移，也承载运行时。从 `team-workflow` 开始的新任务默认使用团队流程。独立调用 MATT 保持轻量；一旦进入团队流程，切换方法仍保留该任务的批准、验收及交接要求。

任务平台维护进行中的工作，`.tw/` 保存项目现在仍然成立的知识。词汇、规则和设计决策已有登记原文的，由原文拥有正文。

任务评估分别描述复杂度、业务风险、工作量、依据、未确定事项与所需能力。父方案和拆分任务分别评估。简单任务可以实现后合并评审方案与代码；中等、复杂任务先由具体评审人确认方案。评审人不设固定职级，也不强制独立；已有明确批准和指派时可以直接接续。

## 知识

- **种类**：rule（现行约束）、decision（决策）、lesson（踩过的坑），加上 glossary 与 overview。条目存在即有效；决定改变时，正文改写为新结论，旧做法连同放弃原因、可重新考虑的条件、来源和关键词保留在“放弃过的做法”中。教训不随代码变化删除。
- **写入**：直接编辑 Markdown，与代码同一个 PR 评审。工具只做导航（`tw brief`，有字符预算）和结构检查（`tw check`、`tw audit`），不判断业务结论，也不使用计划令牌、锁、回执或内容指纹。
- **执行绑定**：知识正文与 `.tw/local/` 不参与。`.tw/config.json` 按检查分别绑定。按提交绑定的检查照常绑定 HEAD。只提交知识不会使按内容绑定的检查过期。
- **跨仓**：事实写在契约提供方仓库，其他仓用 `related` 引用；读取共享仓时展示实际的检出目录、HEAD 与未提交状态。

## 本机状态

按[本机状态边界方案](proposals/2026-10-15-local-state-location.md)，项目内本机状态继续放在被忽略的 `.tw/local/`，按检出目录隔离。手工试点输出放在仓库外；`tw audit` 复用清理命令的分类列出不归工具管理的条目和大小，缓存仍按工具目录处理。

共享仓与外部文件路径有两层配置：`${XDG_CONFIG_HOME:-~/.config}/tw/repositories.json` 按 `project.id` 分组提供默认值，`.tw/local/repositories.json` 提供检出目录覆盖，命令行优先。按键逐项合并，别名、仓库身份和外部文件名称保留各自含义；工具只读这两个文件，不自动迁移或克隆。

`tw check` 检查知识条目和已登记原文中的本机材料引用，发行检查另外扫描本仓 `docs/`。只要本机路径第一级不属于 `tasks`、`batches`、`imports`、`validation-active`、`agents`、`cache`、`repositories.json` 就报错；工具目录的布局说明可以保留。

清理先预览 `tw team cleanup`，再按计划应用。整目录删除、`git clean -fdx` 的后果和任务发布方式见[成员说明](member-guide.md#本机材料与清理)。

## 方案与协作

方案按稳定编号分节，保存完整历史。批准绑定明确章节及其依赖内容；新增、删除、依赖调整或实质变化按新旧关系计算影响，未受影响的批准可以继续使用。算法和格式由[分节方案约定](../skills/team-workflow/references/designs.md)维护。

方案交接与实施交接分别记录。接手材料包含当前需求、评估、有效方案与批准、职责、验收方式、知识入口、依赖、自主决定范围、问题责任和下一步，接手者无需旧聊天即可工作。GitHub 读取器只读；写入命令只生成草稿，发布与关闭沿用已有授权。

## 验证

首次独立验收、回归层次与检出能力、端到端链路、本机与 CI 入口、交付证据、缺陷关联及每周复盘，由[业务验收与质量改进标准](../skills/team-workflow/references/business-acceptance.md)统一维护。`delivery_complete` 表示验收、知识处置与交接记录齐全，不表示回归已自动化（见 `automation_status`）。

执行结果绑定实际源码、依赖内容、具体检查及环境；评审绑定任务要求、方案和代码。检查环境声明为无可变外部状态，或由业务仓提供可以确认夹具版本的只读命令。运行期间源码或环境变化时，结果不能通过。

执行记录的 `argv` 保存检查配置的命令模板，保留 `{output}`，核查时与当前模板比较；真正启动进程时才展开为输出目录的绝对路径。产物按项目内相对路径定位，检出目录整体移动或复制后仍可核查；改动命令模板仍使对应运行过期。

## 格式与发布

- 项目数据——配置、任务、方案、平台记录与本地证据——统一使用 `data_version: 1`。
- 发行使用不可变标签，main 只用于开发；指令文本受篇幅预算约束，由发布检查强制执行。
- 自动化测试、隔离代理试用和两位真实成员试点分别记录；正式试点完成前保留候选版状态，不自动提交、外部发布或推广到成员安装。
