## 0 摘要

两件事一起做，因为它们改的是同一批文件，而且第二件事的写法要求约束第一件事的全部新文字。

1. **验收流程**：交付物在哪里被用户使用，验收代理就在哪里按场景做黑盒验收——Web 应用在浏览器，命令行应用在终端，智能体应用在真实对话渠道。场景是验收的基本单位，正向与反向场景各自成条，各有自己的预期、结果和证据。简单任务用团队自己从业务 SOP 写出的场景，全部通过即可交付；复杂任务由测试同事提供用例，团队的场景必须覆盖每一条用例的业务场景。覆盖由代理按语义判断并写成配对文件，工具核对每条用例都已归类、记录逐场景结果、算出每轮通过率；首轮通过率就是会议要的一次通过率。场景集随验收增长：新增或改动的场景做黑盒验收，已通过的场景经沉淀的回归用例回归，回归通过即仍然有效。随交付形态变化的部分（入口、操作工具、观察点、证据、隔离）由项目在接入时声明；人工标记与复测用的看板由项目代理按指南搭建，向 tw 输出契约格式的结果。tw 只定格式、契约与方法指南，与项目平台脚本同一思路。
2. **指令文本**：两个技能的 23 份 Markdown 里，六类补丁话术来自同一个习惯——在误读发生的位置补一句纠正，而非在概念的定义处写清楚。每个概念改为只在一处正面定义，契约只写现行行为，否定链改成肯定句，三类纠正句整句删除。

### 1.2 指令文本

两个技能的 23 份 Markdown 共约 8 万字符，补丁话术分六类：

| 类 | 写法 | 规模 | 例子 |
| --- | --- | --- | --- |

| 3 | "X 不代表／不代替／不算 Y"的防误读句 | 20 余处 | `onboarding.md:10` "模板和环境声明不代表已执行验证"；`team-delivery.md:51` "具名批准不替代实际评审"；`:61` "子任务通过不代表主需求通过"；`contracts.md:190` "源码引用不能证明执行" |

| 5 | 双重否定、"只有……才……" | 11 处 | team-knowledge `SKILL.md:13` "没有新的理由并告知用户前不要重新采用"；`matt-integration.md:3` "只有用户明确授权，才初始化或迁移，普通任务、安装或升级都不算授权"；`designs.md:14` "没有评估不默认为简单任务" |
| 6 | 同一条规则复制到多个文件 | 4 个概念 | 收尾说明的适用条件出现在 4 个文件；简单与中等任务的批准路径写了 6 处；"未指明用例"2 处；lesson/decision/rule 写法 3 处 |

另有一处沉积：`portable.md:25,55-57,89` 写了四个内部函数的签名，代理用不到。

根因只有一个：试点里每发现一次误读，就在误读发生的位置补一句纠正。证据、工具的职责、绑定覆盖的内容、单人任务、批准路径这些概念从未在一处正面定义；一个概念出现在几个文件里，纠正就补几遍。契约改版时记下"和上一版的差别"，而非改写成现行规则。这与教训 2026-10-14 的根因相同：追加比改写容易。

## 2 验收流程的正确逻辑

### 2.1 场景是验收的基本单位

每个需求有一份**场景文件**，放在业务仓库（推荐 `docs/sop/<批次>.yaml`），按原文登记。格式沿用批次 0、1 实际用过的结构：

```yaml
metadata:
  requirement: "<需求名称>"
  batch: "<批次编号，全局唯一>"
  version: 2
  owner: "<场景负责人>"
  sources:
    - {ref: "<PRD、SOP 或测试用例集的位置>", version: "<版本或哈希>", confirmed_by: "<确认人>"}
sops:
  - id: SOP-02
    title: <业务节点>
    actor: "Owner / Admin"
    entry: "<该节点的用户入口>"
    must: ["<节点必须保持的业务结果>"]
    scenarios:
      - id: SOP-02-P01
        polarity: positive
        title: <正向场景>
        actor: Owner
        priority: P0
        refs: ["ORG-01"]
        verify: browser                   # 验收入口名，须在 .tw/config.json 的 acceptance_entries 中声明
        initial_state: ["<前置状态>"]
        steps: ["<用户会做的操作>"]
        expected: ["<用户可观察的结果>", "<数据或状态变化>"]
        forbidden_effects: ["<不应发生的副作用>"]
        evidence_hints: ["<证据位置提示>"]
        regression: {check: "e2e", cases: ["TC_OBS_001"]}   # 沉淀后的回归用例；缺省表示尚未沉淀
      - id: SOP-02-N01
        polarity: negative
        negative_type: permission
        ...
```

规则：

- 每个节点至少一条正向、一条反向场景；确实没有反向场景的节点写 `negative_exempt` 理由。反向场景的 `negative_type` 取标准第 4 节的负向类型。
- 每条场景有自己的 `expected`，执行后有自己的结果和证据。场景的内容指纹覆盖 `initial_state`、`steps`、`expected`、`forbidden_effects`；指纹变化的场景按新场景处理。
- `regression` 记录该场景沉淀后的回归：`{check, cases}` 指向登记的检查与用例；`{manual: <原因>, owner, trigger}` 表示仍需手动；`{pending: <延期问题编号>}` 或缺省表示尚未沉淀。
- 方案的验收节引用节点：`- 场景：docs/sop/<批次>.yaml#SOP-02、SOP-03`。验收节保留 `依据`、`检查`、`验证`；角色、初始状态、步骤、预期、反例五个标签由场景文件承载。场景文件的 sha256 进入验收节的绑定——文件变化时验收节"内容已改"，受影响的批准与验收重审。
- 自动检查（单元、集成）继续按 `检查` 登记；一个验收节在其检查通过且其场景全部通过时通过。
- `tw team scenarios check <文件>` 校验结构：必填字段、编号唯一、来源非空、负向类型、每个节点的正反向齐全、`verify` 已声明；错误报原文行号。工具只核对结构，场景在业务上是否充分由评审负责。

### 2.2 用例集：自写场景，或覆盖测试同事的用例

| 任务评估 | 场景来源 | 交付条件 |
| --- | --- | --- |
| 简单 | 团队从业务 SOP 写场景，来源由业务负责人或测试同事确认 | 场景全部通过；受阻的场景有处置 |
| 中等 | 同上；测试同事已提供用例时按复杂任务处理（D1） | 同上，或同下 |
| 复杂 | 测试同事提供用例集；团队的场景作为执行集合，覆盖每一条用例 | 场景全部通过，且每条用例都已覆盖或已处置 |

表中的条件是业务验收通过的条件。整体交付另按标准第 5 节：应沉淀的场景尚未自动化时，整体交付记为未完成（D3）。场景验收通过后随业务累加，全量黑盒回归一次要花数天，所以每条应沉淀的场景都要落成仓内回归用例。

**导入**：`tw team scenarios import-cases --task <身份> <文件>` 读取用例清单，保存导入快照与指纹。工具只要求文件是 YAML 子集或 JSON，顶层有一个用例数组（键为 `test_cases` 或 `cases`），每条有 `id` 和 `title`；其余字段原样保存供代理阅读。测试同事现有的 YAML（`metadata` + `test_cases[]`）直接满足这个要求。用例集随需求增长：测试同事补交用例时再次导入，历次导入的并集就是本需求要覆盖的用例（D2）。用例文件的位置由项目决定。

**覆盖由代理判断**：同一业务语义在两边的文字表达可以不同，所以覆盖是语义判断，由代理完成——读完用例与场景后，为每条用例写出覆盖它的场景，缺少时新写场景，预期有分歧时以测试同事的理解为准改场景（会议："以测试上下文为准"），然后写成配对文件。工具核对的只是结构：每条已导入的用例出现在且只出现在一类中，引用的编号存在。`tw team scenarios coverage --task <身份> --pairs <配对文件>`：

```json
{"covered":  [{"case": "TC_OBS_002", "scenarios": ["SOP-02-N01"], "note": ""}],
 "conflict": [{"case": "TC_OBS_007", "scenarios": ["SOP-03-P02"], "note": "预期不同：测试要求拦截，场景写的是提示；待测试确认"}],
 "disposed": [{"case": "TC_OBS_011", "state": "blocked|deferred|out-of-scope", "reason": "", "confirmed_by": "<测试同事>"}]}
```

- 存在 `conflict` 或未归类用例时，`coverage` 报告 `error_code: scenario-coverage-incomplete`，`accept` 拒绝。
- BLOCKED、待评审、V1-SKIP 的用例进入 `disposed`，由测试同事确认。
- 预期写"以实现为准"或"或等价文案"的用例，覆盖它的场景只断言已确认的部分，其余在首轮执行后交测试同事确认。

### 2.3 场景验收是流程的固定步骤

流程从四步改为五步：`start → run → scenarios submit → review → deliver`。

**验收材料与产品指纹。** 本任务的验收材料是方案原文（文件头 `design`、`task` 与本任务相同的 Markdown）及其验收节引用的场景文件。验收材料不计入改动范围；场景轮次绑定**产品指纹**，即排除验收材料后的源码指纹，所以补写或修改场景只影响被改动的场景。检查运行照常绑定包含场景文件的源码指纹，因为项目沉淀的回归可能读取场景文件。

**只执行需要黑盒验证的场景。** `tw team scenarios pending --task <身份>` 按当前产品指纹与场景文件算出待执行清单。一条场景在以下任一情况下有效，其余进入清单：

- 在当前产品指纹上有 `pass` 结果；
- 在更早的产品指纹上有 `pass` 结果，且它的 `regression` 指向的检查在当前源码的有效运行中通过（`cases` 全部通过）。

新增的场景、内容指纹变化的场景、上次 `fail` 的场景、`regression` 缺省且产品源码已变的场景都在清单里。验收时发现遗漏的场景直接追加到场景文件，只有它们需要黑盒执行；已通过的场景由沉淀的回归用例代为回归。

**执行者**是未参与实现的会话——人或代理均可。它按项目声明的验收入口，逐条经交付物本身执行清单中的场景（见 2.5），每条写一行结果：

```json
{"scenario": "SOP-02-N01", "status": "pass", "actual": "<实际结果>", "evidence": ["scenarios/r1/SOP-02-N01/screen.png"],
 "executed_at": "2026-10-16T08:00:00+08:00", "executor": "codex:task-abc", "session": "<会话标识>"}
```

`status` 为 `pass`、`fail`、`blocked`、`skip`。证据文件放在任务目录下本轮的子目录。

**登记**：`tw team scenarios submit --task <身份> --results <文件>`。工具：

1. 核对清单中的每条场景都有结果，证据文件存在且指纹一致，`executor` 独立于 `roles.implementation_owner`。
2. 记录本轮绑定：每条结果对应的场景内容指纹、产品指纹、执行版本、轮次编号。
3. 算出统计：本轮执行的通过、失败、受阻数；每条场景首次执行的结果汇总为**一次通过率**；有测试用例时经配对文件给出按用例的覆盖通过数。
4. 写入 `current.json` 的 `scenarios` 材料；`status` 显示通过、失败、受阻、待执行的数量，待执行数大于零时下一步指向 `scenarios pending`。

`blocked` 的场景需要已知问题中的处置（`accepted` 或 `deferred`，含确认人）；`fail` 阻止验收；`skip` 需要写明理由并计入未验证。

**结果契约对来源中立**：上面的 JSON Lines 就是结果契约。代理直接写它；人工执行与测试同事的复测经项目的看板或转换脚本输出它（见 2.5）；三者都用 `scenarios submit` 登记，`executor` 写执行者。同一场景的多轮结果按执行者对比，"代理判通过、人工复测仍通过"的比例由此得出。工具记录数字，门槛由团队另定（D6）。

### 2.4 验收记录与评审

- `accept` 对每个验收节核对：检查通过，引用节点的场景在当前有效轮次中全部 `pass` 或已处置；记录本轮通过率到验收报告。观察记录的种类为 `execution`（登记的检查）和 `scenarios`（场景轮次）两种；`manual` 由 `scenarios` 取代——人工执行也按场景逐条记录，`executor` 写人名（D5）。
- `review.md` 的"人工观察"段改为"场景执行"段：工具预填本轮的场景、状态、实际结果和证据路径，评审人逐项复核；失败与受阻的场景自动进入问题清单。
- `status` 的步骤序列加入"场景验收"；`run` 在必需检查通过且当前有效轮次全部通过后准备评审稿，否则下一步指向 `scenarios submit`。
- `metrics` 按任务列出各轮通过率与首轮通过率，供每周复盘。
- 交付报告的 `automation` 由工具从场景文件的 `regression` 字段与当前运行生成，按场景编号列出三种状态：`automated`（指向的检查在当前源码通过）、`manual-only`、`pending`（`regression` 缺省或写 `pending`）。手工填写的 `automation` 退役。`verify` 把 `pending` 的场景逐条列在 `regression_pending` 下，整体交付按标准第 5 节记为未完成；`delivery_complete` 的含义保持为验收、知识处置和交接记录齐全。

### 2.5 验收入口与复测看板由项目提供

tw 负责与应用类型无关的部分：场景格式、覆盖的结构核对、结果契约、待执行清单、通过率。随项目变化的两样东西由项目提供，tw 给契约和指南，由代理在接入时为项目生成，与项目平台脚本同一思路。

**验收入口**：`.tw/config.json` 新增 `acceptance_entries`，每个入口回答四个问题：最终用户在哪里验收、执行者用什么工具以用户身份操作、结果在哪里能被看到（含不应发生的副作用）、证据怎么冻结、环境怎么隔离和清理。

```json
"acceptance_entries": {
  "browser": {"surface": "web", "address_env": "E2E_BASE_URL", "operate": "浏览器工具按场景点击与输入",
              "observe": ["页面状态", "网络请求", "相关数据表"], "evidence": ["截图", "控制台", "请求记录"],
              "accounts": ["e2e-owner"], "isolation": "每轮独立租户，结束后清理"},
  "cli":     {"surface": "cli", "operate": "对按安装文档装好的交付物执行用户会敲的命令，临时 HOME 与工作目录",
              "observe": ["标准输出", "错误输出", "退出码", "前后文件清单与哈希"], "evidence": ["命令原文", "完整输出", "文件差异"],
              "isolation": "每轮新建临时目录"},
  "chat":    {"surface": "agent", "operate": "扮演场景中的用户，在真实渠道多轮对话",
              "observe": ["回复", "调用轨迹", "业务动作", "写入的数据"], "evidence": ["完整对话", "轨迹", "运行清单哈希"],
              "isolation": "每次运行唯一标识，会话隔离"}
}
```

tw 只核对场景的 `verify` 指向已声明的入口，以及入口字段齐全。

**复测看板**：人工逐条标记场景、复测代理判通过的场景、查看通过情况，这些界面由项目自己搭建——沿用测试同事现有的工具加一个转换脚本，或由代理为项目生成一个最小看板。`references/scenarios.md` 给出看板契约：读取场景文件与 `tw team scenarios pending --format json` 的清单；提供状态、实际结果、证据与缺陷链接的填写；输出结果契约文件与证据目录，由 `scenarios submit` 登记。看板的位置、启动方式和维护人写进项目验收方案并登记到 `context`，`.tw/config.json` 没有新字段。

三种形态的做法写在同一份 `references/scenarios.md`：命令行应用操作交付物本身而非源码内部函数，在临时 HOME 执行，负向场景含错误参数、缺文件、权限不足、重复执行、中断续接、并发；智能体应用沿用 `test-capability.md` 第 7.5 节的三层验收，扮演用户的执行者与语义复核者分开，在同一快照下重复运行并分别统计机械失败率与语义偏差率。一个需求可以跨多种形态，每条场景用 `verify` 标明自己的入口。

## 7 决定（2026-10-16 确认）

| 编号 | 决定 |
| --- | --- |
| D1 | 中等任务：测试同事已提供用例集时按复杂任务处理（必须覆盖）；没有时按简单任务处理（自写场景）。复杂任务必须有测试同事的用例集，缺少时 `accept` 报告缺口 |
| D2 | 覆盖是语义判断，由代理完成并写成配对文件，工具只核对结构；导入的用例要转换成团队自己的场景。用例集是历次导入的并集，随需求增长；工具中没有按需求编号或标签圈定范围的逻辑 |
| D3 | 回归未沉淀时整体交付未完成，标准第 5 节与全局指引保持现行写法。理由：场景验收通过后业务持续累加，全量黑盒回归一次要花数天。因此每条场景的 `regression` 记录沉淀结果；新增或改动的场景做黑盒验收，已通过的场景经 `regression` 回归，回归通过即有效；`automation` 由 `regression` 生成，`regression_pending` 逐条列出 |
| D4 | 场景只在场景文件中：方案验收节引用节点，内联的角色、初始状态、步骤、预期、反例五个标签退役。每个任务至少一份场景文件；换来一种格式、一处定义、场景修订与方案修订分开版本化 |
| D5 | `manual` 观察由场景轮次取代：人工执行者按同一格式逐条记录，`executor` 写人名；纯文档任务的场景 `verify: doc` |
| D6 | 职责划分：tw 定义结果契约、`submit`、待执行清单与统计，并在 `scenarios.md` 给出看板契约与搭建指引；复测看板由使用 tw 的项目代理按指南为项目搭建（沿用测试同事现有工具加转换脚本，或生成最小看板），向 tw 输出契约格式结果。tw 自身没有看板、执行表或任何团队专用的导出格式；SOP 复测草案标记为被本方案取代 |
| D7 | 定义落位与删除规则按第 3 节表执行；段 2a、2b 并行，在同一工作区进行 |
| D8 | 本方案作为独立任务，由新 Issue 跟踪，在当前分支 `feature/unified-redesign` 上实施；Issue #5 第 3 段排在本方案之后 |
