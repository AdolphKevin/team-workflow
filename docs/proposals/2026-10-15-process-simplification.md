## 0 摘要

把重复手写的部分交给工具，判断仍由人做，所有门槛不变。

- **固定材料组**：每步成功后，工具记录本任务当前有效的材料组。后续命令只需 `--task <身份>`，不再手传 6 个路径。工具按记录取材料，不按时间猜“最新”；有歧义时拒绝。
- **评审改为 Markdown 填写**：
  - 评审人只写结论和理由，工具生成评审 JSON、自动检查的证据引用和问题历史；
  - 源码变化后，工具预填上一轮结论并标为“待复核”，评审人仍须逐项确认，不自动沿用。
- **两个合并命令**：
  - `start` 合并 prepare 和 resume；
  - `deliver` 按顺序调用业务验收、知识核查、最终交付，每步照常记录，失败照常保留。
- **参数归位与 status**：
  - 48 个全局参数归入各自的子命令；
  - status 只列已核实的记录、发布状态和下一条命令；
  - 写明 Issue 的关闭规则。
- **延后**：增量复审链、检查声明输入范围。先按本方案实测，再决定是否需要。

## 2 原则

1. 三道门不变。工具核对事实，判断由人做；不能由工具代替独立执行者生成操作、观察人和数据结果。
2. 能从已有记录推导出来的，就不让人再写一遍。
3. 工具选用的材料必须可以说明来源：按记录固定，不按时间猜。
4. 新规则必须对应真实失败；删除和延后的做法写明原因。

## S1 固定材料组与 `start`

- `tw team start --task <任务文件或身份>` 合并 prepare 和 resume：
  - 第一次运行建立任务目录与准备上下文；
  - 再次运行即为续接，报告停在哪一步。
- 每个成功的步骤更新任务目录中的 `current.json`，记录当前有效材料的路径与指纹：
  - 方案版本、批准、选中的运行、评审、验收、交付。
- 后续命令只要 `--task <身份>`，工具按 `current.json` 取材料，并核对指纹。以下情况一律拒绝，并给出指定材料的命令：
  - 材料缺失或已被改动；
  - 平台上的方案或要求比记录新；
  - 同一角色有两个候选。
- 显式传入的路径优先，同时写进 `current.json`。
- 请求指纹包含解析出的材料组，同编号重试不会返回别组材料的结果。

## S2 `deliver`：顺序封装

- `tw team deliver --task <身份> [--reason <不需要更新知识的理由>]` 依次执行：
  1. 本任务还没有当前的业务验收时，先调用业务验收；
  2. 生成交付报告，从 git 差异预填知识文件；
  3. 最终交付核查。
- 每一步照常写出原有记录；任何一步失败就停在那一步，并保留失败记录。
- 门槛与现在完全相同：
  - 业务验收仍需独立评审与观察；
  - 验收之后改了材料要重新验收；
  - 知识必须正好列出，或写明理由。
- 要改知识时，顺序仍是先 `accept`，再写知识，最后 `deliver`。

## S3 评审改为 Markdown 填写

- `tw team review --task <身份>` 生成 `review.md`：
  - **文件头**：任务、绑定的源码与运行，由工具填写；
  - **每个验收项一节**：工具预填当前运行中对应检查和用例的实际结果，评审人写通过或不通过及理由；
  - **人工观察**：由观察人填写操作、观察结果和数据，工具不代填；
  - **问题清单**：用 Markdown 列表书写，编号、负责人、影响范围、阻塞阶段由评审人填写，工具校验格式和历史一致。
- `review --submit` 把 Markdown 转成现有的评审 JSON，补上自动检查的证据引用和问题历史，然后按现有规则核查。
- 源码或运行变化后再运行 `review`：
  - 工具预填上一轮的结论，每项标为“待复核”，并附上变化文件列表；
  - 评审人必须逐项改为“已复核”，或改写结论；
  - 有未复核的项就不能提交。
  - 不自动沿用任何结论。
- 清理工具同时识别 `review.md` 与生成的 JSON，不删除仍被引用的评审和运行。

## S4 参数归位与命令名

- 48 个全局参数归入各自的子命令，全局只保留 `--root` 和 `--repository`。同步修改外层 `tw` 的参数注入（cli.py:94–99）。
- 新增 `start`、`deliver`、`review`、`accept`，取代 prepare、resume、review-template 加手写评审、verify --phase acceptance。
- 其余命令名（handoff、progress、issue-draft、design-diff 等）是否按 C 节改名，见 D1。
- `run --capture-only` 只捕获源码状态，不算检查完成。

## S5 status 与关闭规则

- status 只把已核实的记录算作完成，生成的模板不算，并列出：
  - 已核实的记录；
  - 收尾说明或交接的发布状态；
  - 下一条命令。
- 删除恒为 False 的验收、交付字段。全部完成时显示“已交付；关闭需要授权”。
- 方案或检查规则变化后，受影响的步骤显示为过期。
- 在 team-delivery.md 写明 Issue 的关闭规则：
  - 前提：最终交付完成，收尾说明或交接已发布，并记录了关闭授权；
  - 工具只报告 `closable`，不执行关闭。

## S6 去掉格式陷阱

- `start` 按固定的方案版本生成任务文件的验收项，不再要求人手抄一份。逐字一致检查保留，但由工具保证满足。
- 待定事项仍用问题对象，以免丢失编号与负责人；拒绝信息附上示例和生成命令。
- 每个拒绝信息都附上修正命令。

## 3 延后与不做

- **增量复审链**：延后。仅凭“变化文件已复审”，不能证明业务影响已被覆盖；例如改了共享校验函数，没改的页面的权限验收也可能受影响。按 S3 逐项复核实测之后再评估。
- **检查声明输入范围**：延后。范围声明不能证明依赖完整：生成脚本或业务配置不在范围内时，旧的通过结果会继续有效。而且牵动文件增删、外部仓库和可携带结果（validation.py:108–114，portable.py:214–221、441–448）。
- **轻量路径的新判定规则**：不做。只合并命令，不新增分级门槛。
- **不做**：降低三道门，自动提交、发布或关闭，成员试点（阶段 4），业务仓迁移（阶段 3、5），改动知识格式。

## 4 验收

**真实入口实跑**：
- 本仓一个小任务、一个中等任务，各从 `start` 走到 `deliver`；
- 中等任务中途改一次源码，触发 S3 的逐项复核。

| 指标 | 基线 | 目标 |
| --- | --- | --- |
| 手传的材料路径 | 每步 3–6 个 | 0 个（只有 `--task`） |
| 不改知识的小任务的命令数 | 6 步，另加手写评审与交付报告 JSON | 4 步：start、run、review --submit、deliver，不写 JSON |
| 评审人手写的证据引用 | 约占评审的三分之一 | 0 |
| 全局参数 | 48 个 | 2 个 |
| status 把模板计为完成 | 是 | 否 |

**反向场景**：以下情况必须被拒绝：
- 缺评审，或评审人是实施者；
- 未验收先交付；
- 漏列知识；
- 有“待复核”项未处理；
- 同一角色两份材料产生歧义，或固定材料被改动；
- 平台方案比本地记录新；
- 中途中断后续接时混入另一组材料；
- 旧批准被复用到新方案；
- 清理之后再次核查。

这些场景写成批次 1 场景文件，交给未参与实现的验收者在隔离工作区执行（合并方案 V3）。

## 6 已确认的决定

- **D1**：只新增 start、deliver、review、accept 四个命令，并把参数归入各自的子命令；其余命令名不改。
- **D2**：评审改为 Markdown 填写；变化后逐项复核，不自动沿用（S3）。
- **D3**：增量复审链与检查输入范围延后，实测后再议。
- **D4**：`deliver` 作为顺序封装，门槛不变（S2）。
