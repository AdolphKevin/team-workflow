# 教训闭环：出现记录、升级为规则与定期复盘

> 状态：已确认，已实施（1.2.0）。日期：2026-11-08。用户的确认见第 7 节；独立验收结果见[验证记录](../validation.md)后，用户答复“现在提交、合并并发行 1.2.0”（2026-11-09）。
> 依据：[magpie](https://github.com/yetone/magpie) 的 `CLAUDE.md`、`AGENTS.md`、`LESSONS.md`、`docs/code-standards.md` 与 `docs/contributors.md`（2026-11-08 读取）；本仓与使用项目的实际记录（第 2 节）。使用项目的查询与原文保存在执行者本机，公开文本只写通用描述。
> 基线：本仓 `ca9d1f4`（1.1.0）。发行版本升为 1.2.0。

## 0 摘要

tw 是各项目共用的团队知识库：每个项目在自己的 `.tw/` 里积累规则、决策与教训。magpie 用一本错题本让教训形成闭环：定期回看提交找出新教训，每条教训记下出现在哪几天，同一教训出现满 3 天就从经验变成评审逐条核对的硬规则，做对的提交也记下来。本方案让每个使用 tw 的项目用现有的条目结构建立同样的闭环：

1. rule、lesson 可加“出现记录”：每次一行，写日期、证据与后果。次数取不同日期的个数，`brief` 在标题旁显示“出现 N 次”。
2. 教训在 3 个不同日期出现后升级为 rule：`tw check` 给出警告并列出日期，`tw audit` 列出反复出现的条目。升级与其他知识改动一样经 PR 由用户确认。
3. 教训标题写成一句要遵守的做法；可加“做对的例子”，记录照着做对的真实提交。
4. 技能提供定期复盘指南：按返工、不该合入、验证太粗三类回看一段时间的提交，结果是一个只改知识的 PR。
5. 评审改动时以改动的文件读取知识，逐条核对其中的规则；`tw init --guidance` 写入项目的指引块写明这一点。
6. 本仓知识按新格式整理，并记录本设计的决策。

读取方式沿用按任务与路径选取。

## 2 现象与根因

| 编号 | 现象 | 根因 |
| --- | --- | --- |
| L-1 | 一个 AI 服务仓 2026-10-29 的会话重复了已有教训记录过的错误，用户提醒“这个做法之前不就踩坑过了吗”后代理才读到。修复提交在正文里加了一句“用户 2026-10-29 再次否定……”，并更新来源与核实基线；标题仍描述过去的现象（某类诉求“曾被误识别为新案件”） | 复发只能写成散文，没有日期与次数，读者无法把它与只出现过一次的教训区分；标题写现象，只看到索引行时读不出该怎么做 |
| L-2 | 本仓教训“每遇到一个问题就加一条规则…”：10-11 至 10-16 间，阶段流程与评审人限制加入后又删除，adopt 同一天删了又加回 | 经验何时成为强制规则，只有“须有一次真实失败”一条判据 |
| L-3 | 验收看板仓库的一条教训把多次事件写成一段：沙箱自检通过而真实冒烟发现问题、只核对函数漏掉对外响应中的私有字段、沙箱拒绝启动原生程序，之后又追加一大段例外说明 | 多次出现没有统一写法，日期与次数缺失，无法判断它是否该成为规则 |
| L-4 | 本仓 1.1.0 验收第 1 轮，会话收到 `command not found: tw` 后跳过读知识；指引块随后改写，原因只写在验证记录，`.tw/` 没有对应教训；第 2 轮同一场景的会话仍在改完后才补读 | 返工要回看才显现，实现者收尾时的判断漏掉了它；目前只在用户要求时回看历史 |
| L-5 | `brief` 对 rule 与 lesson 同样排序展示；技能只写开工前读取，没有写评审时怎样使用规则 | 规则的约束力只体现在措辞上，评审环节没有对应用法 |

## 3 改动

### 3.1 出现记录

rule、lesson 可以有 `## 出现记录` 一节，在条目第二次出现时添加：

```markdown
## 出现记录
- 2026-10-14：<出错的提交、Issue 或验收记录>，<发生了什么与后果>
- 2026-10-29：<复发的提交或会话证据>，<发生了什么与后果>
```

- 第一项写最初那次。日期取该项所引证据的日期：出错、回滚或返工的提交，失败的验收，复发的会话。
- 次数为不同日期的个数，同一天多次算一次；没有这一节的条目算 1 次。计数只从这一节得出，文件头不增加字段。
- 出现位置在条目 `scope` 之外时，把该位置加进 `scope`，范围随证据扩大。
- 追加出现记录属于改写条目：核对条目在当前代码中仍然成立，再更新 `verified`；1.1.0 的基线警告照常提示。
- `tw check` 核对 rule、lesson 的这一节：每项以合法的 `YYYY-MM-DD` 开头、不晚于当天、日期后有内容；不符合时报错并写明第几项。

### 3.2 升级为规则

- 教训的出现记录达到 3 个不同日期时，`tw check` 给出警告：“出现记录有 3 个不同日期（…），按写作规范升级为 rule”。
- `tw audit` 增加“反复出现”一节：列出 2 个以上日期的 rule、lesson，按次数和最近日期排序，标出待升级的教训；JSON 保存日期。
- 升级做法写入写作规范：
  1. 把条目移到 `rules/<slug>.md`。首段写必须保持的做法、条件与例外；`## 依据` 浓缩原来的现象与根因；出现记录与做对的例子原样保留。
  2. 文件头沿用，核对后更新 `verified`；其他条目的 `related` 改指新路径，`tw check` 会报出失效的关联。
  3. 有能自动发现它的测试或验收场景时写进 `guards`。
- 升级后再出现，照样追加出现记录。规则仍反复出现说明人工核对不够，优先补能自动发现它的检查。
- 升级与新增条目同样经 PR 由用户确认：这是团队把经验定为硬规则的时刻。

### 3.3 标题写做法，记录做对的例子

- lesson 的 `title` 写成一句要遵守的做法，用肯定句；现象放在正文。例：“回放把隐藏条目算成已列出”改为“回放只把输出中可见的条目算作已列出”。`brief` 只列出索引行时，代理从标题就知道该怎么做。
- rule、lesson 可加 `## 做对的例子`：照着做对的真实提交与做法，保留一两项最有代表性的。
- 标题句式由评审把关，`tw check` 只核对结构；已有条目在下次改写时调整。

magpie 的一条教训与 tw 条目的对应（成员说明收录此表）：

| magpie | tw |
| --- | --- |
| `**<一句话规则>**` | `title` 与正文首行 |
| 哪个提交或 Issue 出的事、后果 | 正文“现象”，复发写进出现记录 |
| 修复的提交 | `source` 与“修复与防护” |
| `Done right: <做对的例子>` | `## 做对的例子` |
| `Seen N× (YYYY-MM-DD, …)` | 由出现记录计算，`brief` 显示“出现 N 次” |

### 3.4 brief 显示出现次数

- 完整条目的标题后写“（出现 N 次）”，索引行的选中依据后写“；出现 N 次”，N ≥ 2 时显示。
- JSON 每个条目增加 `occurrences`（日期列表）。
- 选取与排序规则不变。项目中没有出现记录时，输出与 1.1.0 相同。

### 3.5 评审逐条核对规则

- `SKILL.md`：评审改动时以改动的文件作 `--path` 读取（文件取自 `git diff --name-only <基线>...`），逐条核对读到的规则，评审意见写明不满足哪一条。
- `tw init --guidance` 的指引块加一句同样的用法；已接入的项目重新运行 `tw init --apply --guidance` 即更新该块。

### 3.6 定期复盘

`references/lessons-from-history.md` 改为“复盘与找回教训”，原“找回历史教训”成为第二节。定期复盘的做法：

1. 范围：上次复盘 PR 说明写明的终点提交之后到当前主干；首次或找不到时取最近 7 天。范围重叠无妨，出现记录中已写明的提交只计一次。
2. 逐个阅读提交说明、改动及关联的 Issue、PR、验收与复验记录，找三类问题：
   - 返工：同一问题修了又修，包括重新打开的 Issue、回滚、同一处的连续修复、验收多轮才通过；
   - 不该合入：合入时检查未通过或缺少项目要求的验收；夹带目标以外的改动；未经用户确认推翻已确认的决策，或重新采用放弃过的做法；
   - 验证太粗：没经过真实入口就称完成；去掉修复后守护的测试或场景仍然通过；说明里没写实际运行了什么。

   同时记下照着已有教训或规则做对的提交。
3. 每个发现用 `tw brief --task "<发生了什么>" --path <涉及的文件>` 找已有条目：同一失败机制就追加出现记录或做对的例子；新的机制用 `tw new lesson` 写成教训；达到 3 个不同日期的按写作规范升级。
4. 运行 `tw check`，提交只改知识的 PR。说明写复盘范围（起止提交）、每个发现及证据、新增与升级的条目，由用户确认后合并。

- 复盘宜由未参与这些提交的代理或成员执行。节奏由各项目决定，例如每周一次，或交给定时运行的代理。
- 技能描述加入“定期复盘提交”，使这类要求能触发技能。
- 验收看板每周质量复盘中的“同类缺陷再次出现”，可按本节记到对应教训；看板标准与模板的修改在 sop-board 另行处理。

## 4 不采用的做法

| 做法 | 原因 | 重新考虑的条件 |
| --- | --- | --- |
| `brief` 每次列出反复出现的条目标题，路径没有选中的也列出 | 用户确认（2026-11-08）：本方案帮助项目产生和维护教训，读取沿用按任务与路径选取 | 真实使用中反复出现的教训因路径未选中而被漏读 |
| 文件头 `seen` 计数字段 | 计数与日期、证据分开写会不一致；多余字段曾导致机械填写（`lessons/2026-10-14-placeholders-committed-to-knowledge.md`） | 无 |
| 单独的代码规范文件 | `rules/` 已是现行约束的位置，多一个位置就多一处维护 | 无 |
| 复盘进度标记文件或配置字段 | magpie 的 `reviewed-through` 停在 10-13，复盘提交持续到 10-28；PR 说明已能给出下一次的起点 | 多人并行复盘、范围频繁重叠 |
| `tw review` 辅助命令：列出范围内提交、疑似返工链与相关条目 | 用户确认（2026-11-08）：先用指南在真实复盘中试行，看清哪些步骤值得固化 | 复盘会话反复手工统计返工链，或漏配已有教训 |
| 按出现次数调整排序 | 次数已显示在标题旁；排序改动会改变已验收的回放结果 | 反复出现的教训因排序靠后而被漏读 |
| 代理自主合入与发行 | 本仓只发行知识技能，合入与发行按团队流程 | 无 |
| 风险闸门、贡献者处理与致谢 | 属于开发流程与 Git 平台 | 无 |

| 场景 | 核对结果 |

## 7 用户确认（2026-11-08）

1. tw 是帮助各项目建立教训闭环的团队知识库，设计从使用 tw 的项目出发；读取沿用按任务与路径选取，`brief` 只显示出现次数。
2. `tw review` 辅助命令本次不做，先用复盘指南试行。
3. 本仓教训的标题一并改写为做法。
4. 实施后由独立代理验收，结果写入验证记录；提交、合并与发行按用户指示。
