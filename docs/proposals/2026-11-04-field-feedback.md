# 实际使用反馈：选择依据、未建知识的仓库、核实基线、结论去向、本机材料与启动器

> 状态：已批准，已实施（1.1.0）。日期：2026-11-04。三项取舍由用户在 2026-11-04 确认（见第 6 节）；验收结果见 `docs/validation.md` 后，用户答复“合并后发行”。
> 依据：一个多仓项目在 2026-10-29 至 11-04 的实际开发会话（核心服务仓、前端仓、AI 服务仓），以及 2026-10-30 记录的 brief 排序失败。查询与输出保存在执行者本机，公开文本只写通用描述。
> 基线：本仓 `7cd1894`（1.0.1）。发行版本升为 1.1.0。

## 0 摘要

1. `brief` 在输出中写明每个条目的选中依据和本次的覆盖情况；指向其他仓库的路径报告该仓库的知识状态和可直接运行的命令。
2. 尚未建立 `.tw/` 的仓库中，`brief` 以 0 退出，指出旧知识目录并给出开工指引。运行时继续只读取 `.tw/`。
3. 条目内容在核实之后被修改、而那次修改保留了原 `verified` 时，`tw check` 给出警告，并写出可照填的当前提交与日期。
4. 技能“完成后”改为一张结论去向表，收尾时把 `.tw/local/<任务>/` 与记忆中的项目结论移入仓库。
5. `tw audit` 按顶层项汇总 `.tw/local/` 的大小、文件数与最后修改时间，限制列表长度，标出 30 天以上未修改的项。
6. 成员说明写明验收看板产品快照与知识提交的关系，由用户选择处理方式。
7. 安装说明提供 PATH 上的 `tw` 启动器；`tw version` 输出可直接运行的完整命令。
8. `brief` 排序打平时按独立信号数取舍，关联边只用于带出条目。

## 1 现象与根因

| 编号 | 现象 | 根因 |
| --- | --- | --- |
| TW-1 | 不带 `--path` 的前端改版任务在核心服务仓得到 3 条无关条目：1 条只因任务含“验收”一词选中，2 条由它关联带出，输出没有任何相关度说明。`--path` 指向兄弟仓库时以 2 退出 | 选中依据只在 JSON 中可见，文本输出没有覆盖情况；仓库外路径被当作非法输入，无法表达“任务改的是另一个仓库” |
| TW-2 | 前端仓尚未迁移，`brief` 以 2 退出，只提示迁移；仓库中 9 张受版本管理的旧卡（4 张与任务直接相关）没有一个代理读到 | 未初始化被当作错误；输出只给迁移方向，缺少开工时如何使用旧知识的指引 |
| TW-3 | 一条规则改了 scope 与 source，`verified` 仍是 3 周前的基线；`tw check` 0 警告，`tw audit` 显示核实后 scope 内有 16 个提交 | 检查只核对基线提交是否存在，不比较条目自身的修改与基线 |
| TW-4 | 7 轮用户产品决定只写在 `.tw/local/` 的草稿里；项目事实分散在两个账号的个人记忆中，其他代理与同事读不到 | 技能只按知识种类说明写法，缺少“哪类结论写到哪里”的去向，也没有收尾核对 |
| TW-5 | `.tw/local/` 中超过 20 MiB 的几十个文件拼成一行；看不出各目录大小和新旧，整轮会话没有运行 audit | 报告逐文件列出、没有按目录汇总、没有修改时间与长度限制 |
| TW-6 | 验收看板把 `.tw/` 计入产品快照，验收轮次中提交的 9 个知识文件被记为产品变化 | “知识与代码同一个 PR”与看板快照的关系没有说明 |
| TW-7 | 每个代理自己查找脚本路径，多个 Claude 配置目录下位置各不相同 | 命令只以技能目录的相对写法给出，没有固定入口 |
| 排序 | AI 服务仓三条订单任务中，最相关的教训排第 28、11、29 名，两次不可见 | 打平时按 `len(reasons)` 取舍，关联边计入，枢纽决策靠 8 条关联边排在前面 |

## 2 改动

### 2.1 选中依据与覆盖说明（TW-1）

- 完整条目的来源行前加“选中：”及依据（如“路径 src/pay/refund.py”“词组“验收””“由 X 关联”）；索引行照常带依据。
- **直接命中**：指定条目、符号、路径或守护测试文件、`--tag`。**间接命中**：任务词组、放弃过的做法的关键词、关联。任务标题下第一行写覆盖情况：
  - 有直接命中：“直接命中 N 条；另有 M 条按任务词组或关联选出。”
  - 给了 `--path` 而直接命中为 0：“本仓知识没有条目覆盖所给路径；以下 M 条只按任务词组或关联选出，先核对是否与任务相关。”
  - 没给 `--path` 且直接命中为 0：“未提供 --path，以下 M 条只按任务词组或关联选出；查明要改的文件后带 --path 再读。”
  - 没有任何条目：“本仓知识中没有与任务相关的条目。”
- `--path` 可以是相对当前目录含 `..` 的路径或绝对路径。落在本仓内的照常规范化；落在本仓外的列入“其他仓库”一节：所在仓库根目录、知识状态（已建立 `.tw/`；尚未建立且有旧知识目录；尚未建立；不在 Git 仓库中），以及在该仓库运行的完整命令 `tw --root <仓库> brief --task "<任务>" --path <仓库内路径>`。`brief` 不读取其他仓库的条目，退出码 0。
- JSON 增加 `coverage`（直接、间接条目数，是否给了路径）与 `outside`（仓库外路径及其状态）。

### 2.2 尚未建立 `.tw/` 的仓库（TW-2）

`brief` 在没有 `.tw/config.json` 的仓库中以 0 退出，输出：

- 本仓库尚未建立 `.tw/` 项目知识。
- 有旧知识目录时：目录位置与其中受版本管理的文件数；开工前按任务词和要改的路径在其中检索、阅读相关旧卡，把它们当作未核实的线索；迁移按 team-knowledge 的迁移指南。
- 没有旧知识目录时：需要记录项目知识时运行 `tw init`。

运行时继续只读取 `.tw/`（决策 `2026-10-14-migration-by-agent` 不变），旧卡由代理直接阅读。`read`、`audit` 照常要求已初始化。TW-1 的“其他仓库”状态与本节共用同一个判断。

### 2.3 核实基线（TW-3）

对带有 `verified.self.commit` 的条目，`tw check` 在以下情况给出警告：

- 已提交：最近一次修改该条目文件的提交在核实基线之后（不是基线提交或其祖先），且该提交前后的 `verified` 值相同、其余内容不同。
- 工作区（`--cached` 时为暂存区）：条目相对 HEAD 有修改，`verified` 值与 HEAD 相同。

警告写明修改所在的提交与日期（工作区修改写“未提交修改”）、原基线，以及核对后应填写的 `{"self": {"commit": "<当前 HEAD 完整提交>", "date": "<今天>"}}`。仅有日期的基线和没有 `verified` 的决策不参与。新增耗时以 100 个条目计控制在 1 秒内。

### 2.4 结论去向（TW-4）

技能“完成后”改为去向表：根因不明显的缺陷 → lesson；难以逆转或确有取舍的选择（含用户确认的产品决定）→ decision；必须保持的行为或契约 → rule；验证环境的操作事实 → 产品仓库的真实验证手册；个人偏好与协作习惯 → 代理或个人记忆；一次性结果与任务过程 → PR 或提交说明；草稿、日志、截图与原始输出 → `.tw/local/<任务>/`。结论写在它所约束的代码所在的仓库；该仓库还没有 `.tw/` 时，先写进 PR 说明并向用户提出初始化或迁移。收尾时通读 `.tw/local/<任务>/` 与本次写入记忆的内容，项目结论按表移入仓库。改写已有条目时，核对后同时更新 `verified`。

### 2.5 本机材料汇总（TW-5）

`audit` 的本机材料一节按 `.tw/local/` 下的顶层项汇总：大小、文件数、最后修改日期与距今天数，按大小降序列出 `--top` 项，其余写成“另有 K 项，共 X MiB”。最后修改超过 30 天的项标出“30 天以上未修改”；查询缓存与路径映射标为工具管理。超过 20 MiB 的文件按大小降序每行一个，最多 `--top` 个，并给出总数。JSON 保留全部顶层项。技能“其他场景”把 audit 写为清理本机材料与查看知识健康的入口。

### 2.6 验收看板快照（TW-6）

成员说明新增一段：工作区接入按快照判断产品变化的验收看板时，`.tw/` 的修改会计入产品变化。由用户选择：在看板中把 `.tw/` 排除在产品快照之外；或在验收轮次进行中把知识草稿写在 `.tw/local/<任务>/`，轮次结束后与代码一起提交。看板侧的提示由 sop-board 实施。

### 2.7 启动器（TW-7）

- 安装说明新增一步：在 `~/.local/bin/tw` 写入两行启动脚本，执行 `python3 ~/.agents/skills/team-knowledge/scripts/tw.py "$@"`。所有客户端与配置目录共用 skills CLI 的这份安装，升级后自动生效。
- `tw version` 增加 `command`：可直接运行的完整命令（`python3` 加 `tw.py` 的绝对路径）。
- 技能正文与 `tw init --guidance` 指引块的命令写作 `tw`：PATH 上有启动器时直接运行，否则为 `python3 <技能目录>/scripts/tw.py`；交给子代理时把 `tw version` 的 `command` 写进交接。

### 2.8 排序打平（2026-10-30 失败）

`Pick.key` 的第三项改为独立信号数：条目理由中去掉“由 X 关联”“与 X 关联”后的条数。层级与路径具体度在前，条目标签在后，规则不变。

在失败当时的项目快照上回放三条记录的查询：教训排名由 28、11、29 变为 15、6、13，三次都出现在索引中（Claude 于 2026-11-04 实验，验收由独立执行者复核）。

## 3 范围

- 本仓：运行时 `brief`、`check`、`audit`、`cli`、`init` 指引块，技能正文，`docs/` 中的设计、安装、成员说明、验收场景与验证记录，本仓 `.tw/` 知识，版本与 CHANGELOG。
- 实际项目中的未落地结论（AI 服务仓改用新框架的决定、开发后台页面含密钥的位置、登录验证码的读取位置、打开会话标记已读、列表闪烁的两个根因）由该项目在自己的仓库中按去向表补写，本方案只记录。
- 看板快照的提示由 sop-board 实施。

## 4 验收

场景加入 `docs/sop/tw-knowledge-only.yaml`，由未参与实现的独立代理经命令行真实入口执行；SOP-13-P01 为独立会话的技能试用。标“本机”的场景使用执行者本机保存的真实输入，只运行只读命令，前后核对 `git status` 不变。

- **SOP-08 选中依据与覆盖说明**
  - P01：临时项目有 `src/pay/` 规则（标签“退款”）和 `src/user/` 教训（标签“验收”）。`brief --task "修改退款金额校验并更新验收" --path src/pay/refund.py`：规则正文写明“选中：路径…”；教训标明只按词组“验收”选中；第一行写直接命中 1 条、另有 1 条按词组或关联选出。
  - N01：同一项目 `brief --task "调整页面布局并更新验收脚本" --path web/layout.tsx`（没有条目覆盖 `web/`）：第一行写明本仓知识没有条目覆盖所给路径，列出的条目只按词组或关联选出；退出码 0。
  - N02：同一任务不带 `--path`：第一行写明未提供 `--path`，提示带路径再读。
  - P02：三个同级临时仓库 A（当前，已建立 `.tw/`）、B（已建立）、C（未建立，有已跟踪的 `.codestable/`），另有一个不在 Git 中的目录 D。在 A 中给出 A 内路径、`../B/...`、C 内绝对路径、D 内路径：退出码 0；A 内路径照常选择；B、C、D 各报告所在仓库与状态，B、C 给出可直接运行的命令；B 的条目内容未出现在输出中。
  - P03（本机）：在 TW-1 的核心服务仓重跑原查询，并加上指向前端仓的路径：第一行写明只按词组或关联选出；前端仓报告为尚未建立 `.tw/`、有旧知识目录，并给出命令。
- **SOP-09 尚未建立 `.tw/` 的仓库**
  - P01：临时仓库有已跟踪的 `.codestable/`（3 张卡片）、没有 `.tw/`。`brief --task ... --path src/x.ts`：退出码 0；写明尚未建立 `.tw/`、旧知识目录位置与文件数、开工前检索阅读相关旧卡并视为未核实线索、迁移指南；输出中没有旧卡正文。
  - P02：既没有 `.tw/` 也没有旧目录：退出码 0，写明尚未建立并提示 `tw init`。
  - P03（本机）：在 TW-2 的前端仓重跑原查询：退出码 0，输出同 P01。
- **SOP-10 核实基线**
  - P01：规则的 `verified` 为提交 X；之后一个提交只改正文。`tw check`：对该条目给出警告，写明修改提交、原基线、当前 HEAD 完整提交与今天日期的填写方式；无其他错误时退出码 0。
  - P02：按警告把 `verified` 改为当前 HEAD 与今天，与另一处正文修改一起提交：警告消失。
  - P03：正文有未提交修改、`verified` 未改：给出警告；把 `verified` 一并改掉后警告消失。`--cached` 对暂存区给出相同结果。
  - N01：`tw new rule --verified-at-head` 新建条目并提交，之后一个提交只改 scope 内代码：没有这条警告。
  - N02：`verified` 只有日期的规则、没有 `verified` 的决策被修改并提交：没有这条警告。
- **SOP-11 排序打平**
  - P01：临时项目有决策 D 与 8 条规则，作用范围都是 `pkg/`，每条规则关联 D 和另一条规则；教训 L 作用范围 `pkg/`、标签与任务词组相同、没有关联。`brief --task "<该词组>" --path pkg --format json`：L 排在 D 与 8 条规则之前；`--budget` 取只能列出部分条目的值时，L 出现在正文或索引中。
  - P02（本机）：在失败当时的项目快照上回放三条记录的查询：该教训三次都出现在正文或索引中。
- **SOP-12 本机材料汇总**
  - P01：`.tw/local/` 下有查询缓存、`repositories.json`、含 2 个超过 20 MiB 文件的 `material-a/`、最后修改设为 60 天前的 `material-b/`、另外 12 个小目录。`tw audit --top 5`：按大小降序列出 5 个顶层项，各带大小、文件数、最后修改日期；写明其余项数与总大小；`material-b/` 标出 30 天以上未修改；缓存与映射标为工具管理；大文件每行一个；JSON 含全部顶层项；所有本机材料保持原样。
- **SOP-13 结论去向**
  - P01（技能试用）：独立会话在只装候选版 team-knowledge 的临时项目中完成一个任务。项目已建立 `.tw/`，`documents` 登记了验证手册，`.tw/local/<任务>/decisions.md` 有一条用户已确认的产品决定草稿；任务说明中给出一条验证环境操作事实，任务过程产生调试日志。收尾后：产品决定写为 `.tw/` 中的 decision；操作事实写入验证手册；日志留在 `.tw/local/`；`tw check` 0 错误。
  - P02：成员说明写明看板快照与 `.tw/` 的关系及两种处理方式，由用户选择。
- **SOP-14 启动器**
  - P01：临时用户目录按安装说明安装候选版并创建启动器，PATH 只加入该 `bin`。在任意临时项目中 `tw version`、`tw brief` 正常；`tw version` 的 `command` 复制运行得到相同版本。
- **回归**：重跑 SOP-01 至 SOP-05。SOP-05 中本仓 `tw check` 0 错误；新警告逐条核对后处理。
