**第 15 项的细节。** 方案里每个自动验收项都写了一行验证要求：

```markdown
- 验证：自动；层级 journey；入口 tw brief、tw team start、tw team status；环境 临时 git 仓库与两个 worktree；替身 无；隔离 isolated；隔离依据 无；用例 无
```

本仓登记的 `unit` 检查声明的覆盖范围是：入口 `tw.py`、环境 `isolated-test-repositories`、替身“项目平台脚本夹具”。工具要求两边满足三条：入口包含、环境逐字相同、替身在方案允许的范围内。两边用词不同，所以全部不匹配。问题有两层：

1. **太晚**：直到最后的业务验收才拒绝。评审稿里写了一句“此检查的覆盖范围不足以独立证明该验收项”，但没有说原因，也没有说怎么改。
2. **太重**：覆盖范围在方案和检查登记处各写一份，只能逐字比对。验证行里的入口和环境，又和同一验收项的“步骤”“初始状态”重复。一个验收项要写 8 个验证字段，写方案的人很难和检查配置用词一致。参考文档本来就写明“覆盖声明本身仍需评审实际测试代码与报告”，逐字比对两份声明，并不能证明测试真的覆盖了场景。

三条比对中，只有替身一条挡住的是真实风险：用记录器代替真实投递的检查，不能证明“消息送达”（`test_recorded_notification_cannot_certify_real_delivery`）。这一条保留，改为写方案时就能看到确切的写法。

## 2 验收绑定

### 2.1 新写法

```markdown
- 检查：unit
- 验证：自动；用例 tests.test_local_state.WorktreeMapping::test_two_worktrees_resolve_their_own_mapping；替身 项目平台脚本夹具
```

```markdown
- 检查：无
- 验证：人工
```

- `验证` 只有三项：方式（自动或人工）；用例（可选，省略等于无）；替身（可选，省略等于无，指方案允许检查使用的替代依赖）。内部结构为 `verification: {method, cases, substitutes}`，删除 `coverage`。
- 用例编号与运行结果中的编号一致，JUnit 格式为 `类名::方法名`。写方案时测试往往还没写，可以先不写用例；评审时由独立评审人补（第 2.5 节）。
- 场景的角色、初始状态、步骤、预期、反例和依据不变。业务入口和环境本来就写在步骤和初始状态里。
- 旧写法（含层级、入口、环境、隔离、隔离依据）直接拒绝，指出行号，并提示改成新写法。按本仓教训“只接受当前格式”，不并存。已发布的旧版本怎么处理见第 6 节。

### 2.2 覆盖范围只在检查登记处声明

`.tw/config.json` 中每项检查的 `coverage`（层级、入口、环境、替身、隔离、隔离依据）保持不变，作为唯一的声明。执行环境、可移植运行记录和自动化回归状态中对检查覆盖范围的使用都不变。

人怎么判断“这项检查能否证明这个验收项”：

- **方案展示**：PR 描述末尾附一张“本方案引用的检查”表，列出每项检查的层级、入口、环境和替身。批准人对照验收场景，就能看到证据来自什么样的测试。
- **评审稿**：每个验收项下列出所用检查的覆盖声明，由独立评审人对照场景和实际用例判断，结论写在“结论”和“理由”中。

### 2.3 工具核对什么

业务验收时：

| 方式 | 保留的核对 | 删除的核对 |
| --- | --- | --- |
| 自动 | 所列检查都在选定的运行中通过；检查的隔离不是“未解决”；检查使用的替身都在验收项允许的范围内；方案和评审中列出的用例都通过；需求级验收所列的检查中至少一项为 journey 层级 | 方案入口包含于检查入口；环境逐字相同；验收项层级与检查层级比对 |
| 人工 | 观察人不是实施负责人；有时间、操作、结果和证据文件 | 观察记录的覆盖范围与方案比对（原来是把方案的覆盖范围原样抄进观察记录再比对，比对不出问题） |

需求级验收必须覆盖完整业务路径，这条规则不变。原来由验收项自己声明层级，现在改为看所用检查的层级。只登记了仓库层入口的检查，层级不会是 journey，仍然不能证明需求级验收（`test_repository_entry_cannot_certify_the_public_entry` 改为按这条规则断言）。

### 2.4 提前核对（第 15 项）

扩展现有的 `contracts.execution_environment`：不运行任何检查，就列出注定无法通过验收的情况，每条都附改法：

| 情况 | 提示的改法 |
| --- | --- |
| 所用检查没有声明覆盖范围，或隔离为“未解决” | 在 `.tw/config.json` 的 `checks.<编号>.coverage` 中补全 |
| 检查使用了验收项没有允许的替身 | 给出可以直接粘贴的写法，例如“在 A1 的验证行加 `替身 项目平台脚本夹具`”；或者改用不含该替身的检查 |
| 需求级自动验收所列的检查中没有 journey 层级 | 改用 journey 层级的检查，或改为人工验收 |
| 方案列出的用例不属于对应检查的格式（命令型检查没有用例） | 删除用例，或改用报告用例的检查 |

引用未登记的检查，现在任务校验就会拒绝，这一点不变。

`design-draft`、`approval-draft`、`start` 都运行这项核对，结果放在 `verification_gaps` 中，文字输出单独一段“验收无法满足”，`next_action` 写出第一条改法。是否阻断见 D3。

### 2.5 评审时补用例

评审稿每个自动验收项增加一个可选字段“用例”，由独立评审人列出证明该验收项的用例。工具核对这些用例确实在选定的运行中通过；没写的，评审稿和收尾说明写明“未指明用例，证据为整项检查通过”。是否对需求级验收强制要求，见 D7。

## 3 任务只存验收编号（第 9 项）

- 任务的书写形式（平台任务块、本地任务文件）中，验收项只写编号：`"acceptance": [{"id": "A1"}, …]`。写了全文的直接拒绝，并提示“验收项只写编号，内容以方案为准”。
- 工具读取任务后，先按所选方案展开出内容和检查，本地任务与平台任务走同一个步骤，子任务按父需求的方案展开。展开后的内部副本保留完整字段，收尾说明、评审等照常使用。
- 需求摘要和需求签名按书写形式计算，也就是只按编号。只改验收内容时，方案出新版本，只有受影响的章节需要重新批准，任务块不用改。
- `issue-draft` 生成的任务块，可读部分列出“编号 + 方案中的章节标题”。
- **迁移代价**：已有任务块从全文改为编号，需求签名全部变化，旧的批准不能沿用，需要重新批准。目前只有 Issue #5 受影响，与第 6 节的格式切换合并处理。

## 4 待确认章节与局部批准（第 11、12、6 项）

- `start` 的结果带出批准状态里的待确认章节，文字输出逐节写明原因，例如“A3：正文已改；T2：依赖 A3；B2：评审人要求修改”，`next_action` 给出可以直接运行的 `approval-draft` 命令。子任务的命令指向持有方案和批准的父需求。
- `approval-draft` 的默认范围：
  - **只批准方案**：本任务需要的章节及其依赖中，状态不是“已批准”的那些（未评审、内容已变、评审人要求修改、暂缓），加上待确认的章节删除；
  - **方案与实现合并评审**：本任务需要的全部章节，绑定当前代码和运行结果，即使方案没变；
  - 没有需要批准的内容时，不生成草稿，直接说明。
- 用 `--sections A3,T2` 指定章节，用 `--sections all` 批准全部章节。
- 批准语句按文档顺序列出章节，写编号和标题。

## 5 发布与措辞（第 4、5、7、8、10 项）

- **发布顺序**（第 4 项）：`design-draft` 的 `next_steps` 写明三步：先完成任务正文、PR 描述等其他编辑；最后生成方案记录并立即发布；发布后不要再编辑之前的评论。工具报“之前的历史已变化”时，指出变化的是哪一条（地址），并提示重新生成。
- **措辞**（第 5 项）：`issue-draft` 的步骤和评审请求不再写死 Issue，改为“在承载方案的变更请求上发布方案记录；没有变更请求时发布在任务上”“请阅读方案原文”。
- **相对链接**（第 7 项）：平台脚本可以选择提供 `file-url --repo --revision --path` 操作，返回 `{url}`；`platform.operations` 的允许列表加入这项操作。生成 PR 描述时，方案里的相对链接改写为发布提交中对应文件的地址。脚本不提供这项操作时，链接改写为纯文本路径，例如 `docs/design.md`，不保留失效的链接。“PR 描述与已发布原文不一致”的提示，按改写后的展示内容比较。本仓的 `.tw/platform.py` 按 GitHub 实现这项操作。
- **关联方式**（第 8 项）：接入指引写明：PR 描述只用于展示方案原文；任务和变更请求之间的关联，由项目平台脚本按项目习惯识别。本仓的做法是在 Issue 正文中写上 PR 地址。
- **历史摘要**（第 10 项）：补一条回归测试：发布方案记录后修改 PR 描述，历史摘要、方案记录和批准都仍然有效。

## 6 格式切换与恢复 Issue #5

**已发布的旧版本。** 工具每次都会从发布提交中重新读取已发布的每个版本，用来计算哪些章节变了。旧写法不再可读之后，Issue #5 已发布的第 1、2 版就成了无法解析的记录。处理办法沿用“方案以 Markdown 原文为准”时的做法：发布一条对账记录，方案历史从第 1 版重新开始，全部章节重新批准。不保留读取旧写法的分支（另一种做法见 D8）。

这批修复推送到 main、本机安装更新后，Issue #5 按新流程继续，作为真实验证：

1. 用 `issue-draft` 重新生成任务块，改为只存编号，并更新 Issue 正文；
2. 方案改为新写法：A1–A7 的验证行改写，A1–A6 写明允许的替身；发布对账记录，以新写法作为第 1 版重新发布方案；
3. `start` 列出待确认章节，`approval-draft` 默认覆盖全部章节，按你此前对该方案的批准授权，以 AdolphKevin 身份发布批准。方案的业务内容不变，只改验证写法；
4. 把 main 合并进 `feature/local-state`，重跑检查，由独立评审人复核，并在评审中补上 A1–A6 的用例；
5. `deliver` 通过业务验收，生成收尾说明草稿交给你确认，合并 PR 由你决定。

局部重新批准已在方案第 2 版时用真实数据验证过（22 节中只重新批准 4 节）。这次重新开始历史，不再重复验证这一点。

## 7 删除与不变

- 删除：方案验收项的层级、入口、环境、隔离、隔离依据；人工观察记录中的覆盖范围；入口和环境的逐字比对；任务书写形式中的验收全文。
- 不变：检查登记处的覆盖声明；替身必须经方案允许；需求级验收必须覆盖完整业务路径或由人工观察；独立验收；用例必须在原始运行中通过；执行环境与隔离规则；自动化回归状态（`automation`）的规则；分节指纹和局部重审。

## 11 待确认的决定

- **D1** 验收项只写检查，以及可选的用例和允许的替身。层级、入口、环境、隔离只在检查登记处声明；检查能否证明验收，由批准人和独立评审人对照检查声明判断。工具不再逐字比对入口和环境，替身仍须经方案允许。
- **D2** 需求级自动验收所列的检查中，至少一项为 journey 层级。
- **D3（建议：只提示）** 提前核对的结果只提示，不阻断起草和开工；业务验收时的拒绝不变。另一种做法是 `design-draft` 直接拒绝生成方案记录。建议只提示，理由有两个：一是第 2.4 节有两种情况改检查配置就能解决，不需要改方案；二是本仓规则要求不增加用户没要求的强制门。
- **D4** 任务的书写形式中，验收项只写编号，写了全文的直接拒绝，本地任务和平台任务一致。
- **D5** `approval-draft` 默认范围按第 4 节，用 `--sections` 指定章节。
- **D6** 相对链接由平台脚本的可选操作 `file-url` 改写为绝对地址；没有这项操作时改为纯文本路径。
- **D7（建议：可选）** 评审中的“用例”是可选字段：写了就核对，没写就在评审稿和收尾说明中写明。另一种做法是需求级验收的检查报告用例时必须写，这样证据会具体到用例，但增加了一项强制要求。
- **D8（建议：重新开始历史）** 旧写法的已发布版本按第 6 节对账，方案历史重新开始。另一种做法是保留一个只用于读取已发布旧版本的解析分支，这样 Issue #5 可以发第 3 版、只重新批准受影响的章节；代价是长期保留一套旧格式解析代码，而目前用到它的只有 Issue #5。

## 评审意见处理

初稿由 Codex 独立评审（只读），采纳的意见：

- 删除替身比对会放过“用记录器代替真实投递”这类问题，因此改为保留替身比对，提前给出可粘贴的写法；
- 已发布的旧版本会被重新解析，直接拒绝旧写法会让 Issue #5 无法继续，因此增加第 6 节的格式切换和 D8；
- 写方案时测试还没写、用例名未知，因此增加评审时补用例（第 2.5 节、D7）；
- `approval-draft` 的默认范围原来只算“未评审和内容已变”，会漏掉评审人要求修改、暂缓的章节和合并评审，因此按第 4 节重写；
- 任务只存编号会改变需求签名，因此写明迁移代价，并要求本地和平台在校验前都先按方案展开；
- 引用未登记的检查现在已经会被拒绝，因此从提前核对的列表中删除；用例示例改为与运行结果一致的 `类名::方法名`；`file-url` 需要加入平台操作的允许列表。

未采纳的意见：需求级验收必须写用例。它会增加一项强制要求，因此列为 D7，由你决定。
