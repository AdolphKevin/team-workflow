## 0 摘要

- Issue 负责需求、拆分和跨仓协调；方案和批准可以记在变更请求（GitHub 的 PR、GitLab 的 MR，下同）上，也可以照旧记在 Issue 上。
- 工具不内置任何平台的代码。平台读取由**项目平台脚本**完成：一个登记在 `.tw/config.json` 中的命令，实现四个只读操作，输出固定格式的 JSON。工具调用脚本、校验输出、保存原始响应，核查规则不变。
- 脚本是**项目的代码**，不是工具的代码。用户在初始化时确认平台和用法后，代理按契约生成脚本，用一致性检查验证，与代码一起评审提交。换平台就换脚本，工具不动。
- 记录格式不变：围栏块、`history_digest`、分节指纹、批准信封、评审 Markdown 第 2 版。批准信封加一个可选字段 `revision`，支持在变更请求上批准。
- 没有平台的项目不配置脚本，沿用现有的本地任务方式。
- 三道门不变。工具和脚本都不向平台写入，不自动提交、合并或关闭。

## 1 现状

平台读取集中在 `github_read.py`（约 80 行），经 `gh` 调用 GitHub API，供 `coordination.py`、`portable.py` 和 `issue_draft.py` 使用。实际只有四类操作：

| 操作 | 现在的用途 | 调用处 |
| --- | --- | --- |
| 读任务 | Issue 正文与全部评论，解析任务块、方案、批准、交接、进度 | `start`、`status`、`issue-draft`、跨仓父任务与依赖任务 |
| 核对提交 | 提交是否存在、内容是否为所称的提交 | 跨仓联合核查、可携带结果 |
| 核对引用 | 提交、文件、Issue、PR、评论链接是否可达 | 依赖证据、契约确认、交接引用 |
| 取持续集成产物 | GitHub Actions 的 run、job、artifact 元数据与下载 | `import-result` 的来源证明 |

问题在于：工具只认 GitHub。换 GitLab、Gitea 或自建平台，就要往工具里加一套；每加一个平台，工具的测试、发布和维护都要跟着走。

## 2 原则

1. **契约在工具，实现在项目**。工具规定“要什么、什么格式、什么算错”；“从哪拿、怎么拿”是项目的事。
2. **脚本取数，代理不取数**。平台数据由脚本一次取回、由工具解析，不进代理的上下文。代理只看工具的核查结论。
3. **只读**。脚本只能读平台。凭据留在平台自己的命令行工具或环境变量里，脚本和工具都不保存。
4. **生成后验证**。脚本由代理生成，必须通过工具的一致性检查，并经人评审后提交，才能用于交付核查。
5. **格式与门槛不变**。只改记录从哪里来，不改记录是什么、要满足什么。

## 3 平台脚本契约

### 3.1 登记

`.tw/config.json` 新增 `platform`，形式与 `checks` 相同：

```json
"platform": {
  "argv": ["python3", ".tw/platform.py"],
  "timeout": 60,
  "operations": ["task", "commit", "reference", "ci-result"]
}
```

- 脚本位置由项目决定，默认 `.tw/platform.py`；`tw check` 不把它当知识条目。
- `operations` 声明脚本实现了哪些操作。`task` 必须实现；其余可选，未声明的操作在需要时给出明确的缺口，不静默跳过。
- 没有 `platform` 时为本地模式（第 5 节）。

### 3.2 操作

工具以 `argv + [操作, 参数...]` 调用，读取标准输出的一个 JSON 对象。退出码非零视为失败，标准错误的首行作为原因展示，不展示其余内容（可能含凭据诊断）。

| 操作 | 参数 | 输出 |
| --- | --- | --- |
| `task` | `--id <任务身份>` | `{"id", "url", "state", "owners", "items": [{"url", "author", "created_at", "updated_at", "body", "kind"}], "raw"}`。`state` 为 `open` 或 `closed`，`owners` 为负责人数组（可为空），`updated_at` 为最后编辑时间，未编辑时等于 `created_at`；这三项保留现有的负责人、关闭状态和历史被编辑的核查。`items` 是任务本身及其全部评论；方案与批准在变更请求上时，一并包含变更请求描述与评审，`kind` 区分 `task`、`comment`、`change`、`review` |
| `commit` | `--repo <仓库身份> --revision <完整提交号>` | `{"exists", "revision", "author", "time"}` |
| `reference` | `--url <链接>` | `{"reachable", "kind", "revision?"}`；`kind` 为 `commit`、`file`、`task`、`change`、`comment` |
| `ci-result` | `--locator <JSON>` `--output <目录>` | `{"provenance": {...}, "archive": "<目录内的文件名>"}`；产物下载到工具给定的目录 |

- `raw` 是平台原始响应，工具原样保存在任务目录，供独立验收对照平台，不参与核查。
- 工具校验：字段齐全、类型正确、`items` 按 `created_at` 再按 `url` 排序、`body` 为原文、`revision` 为完整提交号、`archive` 不越出给定目录。校验失败一律拒绝，不做猜测修复。
- 同一次命令内，同一参数只调用一次脚本，结果缓存在内存。

### 3.3 一致性检查

新增 `tw team platform --check --id <一个真实任务>`：

- 依次调用声明的操作，用该任务的真实数据核对输出格式；
- 对 `commit` 用本地 git 中的一个已知提交交叉核对；
- 报告每个操作的结果和耗时，不输出平台数据正文。

初始化时必须通过；脚本修改后在同一变更请求里重跑，结果写进评审。

## 4 平台适配：初始化时生成脚本

`tw init --guidance` 的指引中增加一步，由代理执行：

1. 调查 `git remote`、本机可用的命令行工具，以及仓库里已有的 Issue、变更请求、持续集成配置。
2. 向用户确认：用哪个平台管需求、方案和批准记在哪里、是否从持续集成导入检查结果。用户不确认，不生成。
3. 按契约（`skills/team-workflow/references/platform.md`，计入发布检查的篇幅预算）生成脚本：优先调用平台自己的命令行工具（`gh`、`glab`、`tea` 等），其次是读取环境变量凭据的 HTTP 请求；只用 Python 标准库。
4. 运行一致性检查，修正直到通过。
5. 把平台选择写成一条决策 `.tw/decisions/<日期>-task-platform.md`：平台、记录位置、凭据来源、脚本路径（作为 scope）。脚本与决策一起随变更请求评审提交。

工具不附带任何平台的实现，也不附带示例脚本。生成质量由一致性检查和人工评审保证。本仓自己用 GitHub，按同样步骤生成本仓的脚本，取代现在的 `github_read.py`，同时作为这套指引的首次试用。

## 5 没有平台的项目

不配置 `platform`，沿用现在的本地任务：任务、方案、批准、评审都是本地文件，命令与校验规则相同。按 T1 的既有说明，本地任务只能在本机续接，不能宣称支持团队交接。

v2 曾提出把记录放在 `.tw/local/` 并以提交证明作者，这不成立：该目录被忽略，不会被提交。确有“无平台、多人交接”的需要时，由项目选择一个入库目录并在平台脚本里读取它，这仍然是一份项目脚本，不需要改工具。

## 6 方案与批准记在变更请求上

- 方案记录块可以放在变更请求描述里，批准记录块放在变更请求的评审里，由脚本的 `task` 操作一并取回（`kind` 为 `change`、`review`）。
- 批准信封新增可选字段 `revision`：批准时变更请求的提交号。有这个字段时，核对它不早于被批准章节最后一次变化的提交；没有时按现有 `design_revision` 规则。
- 分节批准、按指纹计算影响、局部重审、简单任务的合并批准，全部不变。推一版新方案，只有受影响的章节需要重新批准。
- 中等、复杂任务要先批准方案时，先开只含方案块的草稿变更请求，评审通过后再写代码。这是团队约定，写进 Issue 模板；工具仍按现有的 `implementation_ready` 判定。

## 7 命令与材料

| 项 | 变化 |
| --- | --- |
| `github_read.py` | 删除；三个调用模块改为调用平台脚本 |
| `tw team platform --check` | 新增 |
| `start`、`status`、`issue-draft` 等读平台的命令 | 改为经平台脚本读取，参数不变 |
| `import-result` | 来源证明改为经 `ci-result` 操作，校验规则不变 |

| `references/platform.md` | 新增，脚本契约与生成步骤 |

## 8 代价

1. **每个项目多一份脚本**。由代理生成，约 100–200 行，属于项目代码，由项目评审和维护。平台接口变化时，修的是项目脚本，不是工具。
2. **生成可能出错**。一致性检查只能核对格式和一个真实任务，不能保证所有边界（例如评论超过一页）。契约里写明分页、重定向、已删除对象的要求，一致性检查选一个评论较多的任务来测。
3. **持续集成产物差异大**。`ci-result` 是可选操作；不实现时用本地 `run` 的记录，与现在没有持续集成导入的项目一样。
4. **本仓只能在 GitHub 上实测**。其他平台的契约正确性用夹具脚本测试，真实平台由首个使用它的项目在初始化时验证，并如实记录。

## 9 不做

- 不在工具中内置或附带任何平台实现；
- 不向平台写入，不自动合并或关闭；
- 不删除分节方案、指纹、局部重审、评审 Markdown；
- 不新增门槛，不改知识格式。

## 10 验收

1. **契约**：夹具脚本覆盖四个操作的正常输出、字段缺失、排序错误、产物越界、非零退出；工具分别拒绝并给出原因，不泄露标准错误的其余内容。
2. **本仓试用**：未参与实现的代理在本仓的新克隆上，按 `platform.md` 生成 GitHub 平台脚本，通过一致性检查；用它走完一个真实任务——方案块在草稿 PR 描述、批准在 PR 评审——从 `start` 到 `deliver`。改方案中的一节后推新提交，`status` 只报该节需要重新批准。
3. **等价**：本仓在删除 `github_read.py` 前后，对同一批真实 Issue，`start` 与跨仓核查的结果一致。
4. **第二个项目**：在 live-chat 的一个仓库上，由另一个未参与的代理按指引生成脚本并通过一致性检查，记录生成耗时和返工次数。
5. **本地模式**：不配置平台的项目，批次 1 的本地场景全部通过。
6. T7 延后的两个平台场景，在阶段 4 由真实成员完成。

## 12 待确认的决定

- **D1** 工具不内置平台代码；平台读取由项目平台脚本完成，工具规定契约并直接调用。
- **D2** 平台脚本在初始化时由代理按用户确认的平台生成，通过一致性检查、经评审后随项目提交；平台选择写成项目决策。
- **D3** 方案与批准可记在变更请求上；批准信封加可选 `revision`；分节与局部重审不变。
- **D4** 是否让 `deliver` 直接核查变更请求上的评审，省去 `review --submit`。
- **D5** 中等、复杂任务先开只含方案的草稿变更请求，写进 Issue 模板，工具不强制。
