## 1 问题

Issue #5 的业务验收已经通过，交付却停在最后一步：

> Delivery handoff incomplete: Task has no assigned owner; the implementer is not the single assignee; post an implementation handoff instead of a close note

工具只在“Issue 只有一个负责人，且这个负责人就是方案里的实施负责人”时，才允许用收尾说明结束任务；否则要求另发实施交接。方案的实施负责人是 Codex，是代理而不是平台账号，所以这个条件永远满足不了。一个人带着代理完成的任务，本来就是技能说明里的“单人工作”，应当用收尾说明结束，却被要求写一份交给自己的交接。

同一个根源还造成第 20 项：同一检出目录里第二次运行 `start`，工具把它当成“接手别人的任务”，要求有交接记录、Issue 上有负责人。找不到时，它把“准备”这一步标成失败，`status` 又提示重新 `start`，形成死循环。

工具把两件事混在了一起：谁实施（方案中的角色，可以是代理），以及平台上谁负责（Issue 的负责人，是平台账号）。

同批修两个小问题：

- **第 18 项**：方案历史需要对账时，`issue-draft --design` 整个被拒，连任务块也生成不了；不带方案时，可见的验收项只有编号，没有标题。
- **第 19 项**：章节标题本身以编号开头时，待确认章节显示成“A1 A1 两个 worktree……”。

## 2 改法

### 2.1 收尾说明按平台负责人判定（第 22 项）

- 允许用收尾说明的条件改为：Issue 恰好有一个负责人，没有改动需要另行负责的共享仓库，也没有跨服务风险。删除“负责人必须等于方案实施负责人”这一条。后两条条件不变。
- 收尾说明同时写明平台负责人和方案的实施负责人，例如“负责人 AdolphKevin；实施 Codex”。
- Issue 没有负责人或有多个负责人时，规则不变：没有负责人时提示先指派；多人接力仍发布实施交接。

### 2.2 同一检出目录的接续不需要交接（第 20 项）

- `start` 判定为接续，也就是本检出目录里已有同一任务、输入相同的准备材料时，不再要求交接记录和平台负责人。这两项只在接手时检查，也就是本机没有这个任务的准备材料。
- 其他接续检查保持不变：平台上的需求、批准或进度是否变化，验收是否正在运行。
- 接续不会再因为这两项把“准备”标成失败，`status` 也不会再因此提示重新 `start`。

### 2.3 小修

- **第 18 项**：方案历史需要对账时，`issue-draft --design` 照常生成任务块，可见部分带章节标题；不生成方案记录，并提示改用 `design-draft --reconcile`。
- **第 19 项**：标题本身以编号开头时，只显示标题。

### 2.4 不在本批

**第 21 项**：工作区指纹依赖各人本机的 git 全局忽略规则，而 tw 用户级映射所在的 `XDG_CONFIG_HOME` 也会改变 git 找全局忽略规则的位置。直接改为不读全局忽略规则的话，`.claude/settings.local.json` 这类本机文件又会被算作改动，反而拦住交付。这一项需要单独设计，先记录。
