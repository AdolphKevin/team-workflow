## 1 根因

### 1.1 工作区文件清单随运行环境变化（第 21 项）

现象：Issue #5 第一轮复核的误报 Q3。复核代理为隔离 tw 的用户级映射，临时设置了 `XDG_CONFIG_HOME`，随后所有检查都判为“源码已变”。

根因：工作区指纹和改动范围都读取 git 的全局忽略规则，这份规则的位置由 `XDG_CONFIG_HOME` 等环境变量决定。同一检出目录、同样的文件，在两个环境下得到两个指纹。列出未跟踪文件的逻辑分散在六处，各自调用 git：`team/common.py:229`、`team/validation.py:130`、`team/portable.py:46`、`team/knowledge.py:73`、`gitutil.py:34`、`gitutil.py:117`。

### 1.2 交付按“本地有无评审”选择评审（第 23 项）

现象：评审人在变更请求上重新提交评审后，`deliver` 继续核对本地登记的旧评审，停在业务验收。

根因：`deliver` 以本地登记为准，只在本地为空时读取平台（`team/delivery_sequence.py:162`）；工具约定也写着“已有提交不自动替换”。评审人的最新结论可能在变更请求上，选择依据却是登记的先后。

### 1.3 `status` 把每个任务都当作进行中（第 26 项）

现象：2026-10-16 在本仓对已关闭的 Issue #5 运行 `tw team status --task <Issue #5> --format text`：

```
收尾说明或交接已发布：https://github.com/AdolphKevin/team-workflow/issues/5#issuecomment-6209185662
1. [x] 准备任务与知识简报
2. [!] 运行检查（源码已变，需要重做）
……
下一步：运行检查
tw team run --root "$PROJECT" --task https://github.com/AdolphKevin/team-workflow/issues/5
```

根因：`status` 始终用当前检出目录核对检查记录。任务关闭后，检出目录已经切到别的分支，所有步骤随之判为过期。

### 1.4 输出分散在三个出口

现象：出错时 `--format text` 仍打印原始 JSON。

根因：正常结果在 `team/workflow.py` 按 `--format` 输出；输入错误和工具缺陷两个异常分支各自直接打印 JSON（`team/workflow.py:230–240`）。

### 1.5 下一步按报错文字推断

根因：五个模块用报错文字中的英文或中文片段，决定下一步命令和问题所在的小节：`team/repairs.py:58–83`、`team/delivery_sequence.py:142`、`team/reviews.py:721–723`、`team/design_markdown.py:372`、`team/design_markdown.py:516`。文字一改，下一步就跟着变。第 23 项里那条只提 `run` 和 `review --submit` 的提示，就出自 `delivery_sequence.py:142` 的文字匹配。报错文字因此一直停留在中英混杂。

### 1.6 用户可见文字中英混杂

现状：约 400 条报错说明，以及十余条下一步和概要是英文，约 100 条是中文。文字用哪种语言，由各处作者各自决定。

### 1.7 `init` 生成的条目被自己的 `check` 拒绝

根因：`tw new` 要求至少一个 `--source`；`init` 在没有 README 时写入空列表（`init.py:51`），生成的条目被它自己的 `check` 拒绝。此外，`entries.py:183–189` 对同一个空字段报两条问题。

## 2 正确逻辑（替换原有实现）

### 2.1 工作区文件清单由检出目录决定

- 文件清单 = 已跟踪文件 + 仓库规则以外的未跟踪文件。仓库规则指各目录的 `.gitignore` 和本检出目录的 `.git/info/exclude`。
- 由一个函数产出这份清单，六处全部改用它。调用 git 时显式清空全局忽略文件（`-c core.excludesFile=`），清单因此只随检出目录变化。
- 本机文件（如 `.claude/settings.local.json`）写进项目的 `.gitignore`。改动范围列出这类文件时，提示写明文件名，并建议把它加入项目的 `.gitignore`。本仓同批加入 `.claude/settings.local.json`。
- 只靠全局规则忽略过本机文件的检出目录，已有检查记录的指纹会变化一次；进行中的任务重跑一次检查。

### 2.2 交付采用最后提交的评审

- 评审以评审人最后提交的一份为准，提交在变更请求上或本地文件中都适用。
- 平台任务每次 `deliver` 都读取变更请求上含绑定区的最新评审，与本地登记的评审比较提交时间（平台评审取 `updated_at`，本地提交取登记时间），采用较新的一份。较新的是平台评审时，按 `review --from-platform` 的流程登记，然后继续。
- 本地任务只有本地提交，同样采用最后一份。
- 工具约定中“已有提交不自动替换”一句，改写为本规则。

### 2.3 `status` 先确定任务阶段

- 平台任务的 `task.state` 为 `closed` 时，任务处于“已关闭”：`status` 报告各步骤的最后记录，概要为“任务已关闭”，下一步为空。
- 其余任务处于“进行中”，按现行规则用当前检出目录核对记录。Issue 仍打开（包括 PR 已合并）时、以及本地任务，都按进行中核对。

### 2.4 一个输出出口

- 每条命令的结果，包括成功、输入错误和工具缺陷，都交给同一个函数，按 `--format` 输出：
  - `json`（默认）输出现有结构；
  - `text` 输出概要、问题和下一步，工具缺陷另列请求目录和调用位置。
- 退出码保持现状。

### 2.5 下一步由错误代码决定

- 需要特定下一步的每一类错误都带一个错误代码，沿用现有的 `error_code` 机制（如 `current-materials-incomplete`）。问题所在的小节作为结构化字段，随错误一起给出。
- `repairs` 和其余四处只按错误代码和字段选择下一步与小节，报错文字只用于显示。
- 第 23 项提示的问题随之解决：评审绑定的源码已过期时，下一步由错误代码决定。

### 2.6 用户可见文字统一为中文

- 报错说明、下一步、概要等所有给人读的文字统一为中文；命令名、字段名和错误代码保持英文。
- 测试按行为断言：选择下一步的地方断言错误代码；文字本身就是需求的地方（如下一步命令），断言新的中文文字。

### 2.7 `init` 与 `tw new` 采用同一来源规则

- 概览的来源取 `--source`；其次取 `README.md`。两者都缺时，`init` 的预览列出所需的 `--source`，`--apply` 在来源齐全后写入。
- 每个字段的问题只报一条：空值报“缺少必填字段”，类型错误报“必须是非空字符串数组”。

### 2.8 知识与文档

- 新增教训“工作区指纹随运行环境变化”，写明现象 Q3、根因 1.1、修复 2.1，守护测试为 2.1 的测试。
- 新增规则“给人读的文字用中文，下一步由错误代码决定”，守护测试为 2.5 的测试。
- 改写相关文档：工具约定中 `deliver` 的评审一段、团队交付第 47 行、成员说明中本机文件的写法；更新验证记录中的第 21、23、26 项和三项原有问题。

## 5 待确认的决定

- **D1** 工作区文件清单只认仓库规则（`.gitignore`、`.git/info/exclude`）。代价：只靠全局规则忽略的本机文件，需要加入项目 `.gitignore` 一次；已有检查记录的指纹变化一次。
- **D2** 评审以最后提交的一份为准，替换“已有提交不自动替换”。
- **D3** 任务阶段以平台上的关闭状态为准。PR 合并后、Issue 关闭前按进行中核对：平台契约目前只提供 Issue 的打开、关闭状态，而压缩合并会生成新提交，用提交祖先关系判断合并会漏判。
- **D4** 给人读的文字统一为中文；命令名、字段名和错误代码保持英文。
- **D5** `init` 与 `tw new` 采用同一来源规则：项目缺少 README 时需要 `--source`。
