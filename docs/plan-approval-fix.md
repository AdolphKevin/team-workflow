## 原因与复现

1. **新旧任务只按格式区分。** `workflow_v4.handles()` 看到旧版任务块就选择旧流程，
   没有核对它是否真是升级前已存在的在途任务。这解释了第四版项目为何仍能继续使用
   无方案材料的旧链路。
2. **开始实施缺少必经检查。** 当前 `prepare` 能返回 `implementation_ready: false`
   （尚不具备实施条件），但技能没有明确要求每次新建子任务、首次修改源码及派出实施代理
   前都完成这项核对。后续验证工具的成功不能补证之前已经得到批准。
3. **任务拆分指令仍把没有依赖写成可以开工。** `matt-to-tickets/SKILL.md` 第 40、65、79、
   81、105 行仍要求无前置任务即可开始、默认添加 `ready-for-agent` 标签（可交给实施代理）。
   本次 Issue 正文和创建命令也使用了这些表述。团队适配段虽提到方案要求，前面的直接操作
   指令及模板仍与之冲突。
4. **确认对象没有说清。** 需求澄清、某个接口字段的确认、实施顺序的确认，容易被扩大成
   整份方案的批准。长会话继续和工具升级后，旧指令又加重了这种偏差。

已在临时 Git 仓库复现，GitHub 读取用固定输入代替，实际执行本仓命令分派代码：

```text
python3 /private/tmp/team-workflow-plan-gate-repro.py
项目格式 4 + 新 Issue 的旧格式任务块 + 无旧任务延续依据
→ task-export 返回 ok: true，导出格式 2 的任务
→ “新任务不能静默选择旧流程”的诊断断言失败

对照：第四版中等复杂度方案 + 无批准
→ implementation_ready: false，对照断言通过
```

这证明了分派缺口，也表明新版批准计算本身能识别缺少批准。导出成功仅说明导出成功，
并不等于工具授予了开发权限；真正越步还包括代理跳过开工核对。此复现不属于修复后的
回归通过，也不属于独立代理试用。

## 当时拟议的修复（历史，不作为现行入口）

### 1. 建立任务后，先交付可评审的方案

把从需求到实施的顺序放在主技能的必经步骤中：读取知识与原文 → 评估任务 → 形成方案
→ 按该任务适用的评审方式核对批准 → 核对实施条件 → 修改源码或委派实施。

方案至少说明目标与非目标、当前问题、实现方法及涉及模块、接口或数据变化、主要风险、
验证方法、待定事项和负责人。简单任务可以是短方案；Issue 的需求正文或验收清单不能
单独替代实现方法。需要用户决定的内容必须具体到可判断的方案，再提交评审。

保留当前已接受的两条路径：简单任务先形成简短方案和有依据的评估，可以实施后合并评审；
中等、复杂任务先批准方案再实施。未评估的任务进入“待评估”，不能默认为简单任务。
如果用户在具体任务中要求先批准，则该任务遵循用户要求。

### 2. 明确批准覆盖什么

沿用现有按章节和内容指纹绑定的批准机制。记录真实确认来源及其对应内容，核对确认之前
方案是否已经呈现。对需求、字段或顺序的确认，只覆盖实际确认的部分。已有方案批准与
指派可直接复用，避免重复要求开工确认。

新建子任务、恢复会话、首次修改源码、委派实施，以及发现方案实质变化时，必须读取
`prepare` 或 `resume` 的实施条件及缺项。材料生成成功和 `ok: true` 不代替实施条件。
只读调查、隔离复现和必要的基线检查可以继续；未满足条件时，下一步应明确是补方案、
提交评审还是解决待定问题。

实施代理收到的材料应包含任务、对应方案版本、适用批准或简单任务评审方式，以及允许
修改的范围。主代理也受同一规则约束。

任务拆分完成只表示任务边界与依赖已确定。“没有前置任务”只描述依赖状态；团队任务
只有核对实施条件后才能标为可实施。调整拆分技能、模板及多任务实施的选择条件，使它们
都指向同一套开工规则，避免在末尾补一句说明、前面仍要求立即执行。

### 3. 收紧旧任务延续的识别

新任务使用第四版。旧任务继续保留原格式，但采用旧流程应有明确延续依据，至少绑定任务
编号、原格式和原材料引用；不能只靠调用者把 `schema_version` 写成旧值。

在新版项目遇到缺少延续依据的旧格式任务时，允许查看历史材料与运行诊断检查，但明确
报告流程未确认，不得据此宣称可以实施或完成新版交付。补齐真实旧任务依据或明确采用
新版后再继续；不自动改写历史，不把旧材料转成新版通过证明。

项目升级结果及后续入口要提示重新读取已安装技能的主入口和新任务模板，使工具版本、
项目配置和当前会话采用的规则得到同步。

### 4. 改动范围

- `skills/team-workflow/SKILL.md`：必经顺序及何时重新核对。
- `references/team-delivery.md`、`designs.md`、`contracts-v4.md`、`matt-integration.md`：
  批准含义、实施条件、旧任务延续与方法切换的统一约定；正文按职责只维护一份。
- `scripts/workflow_v4.py`、`workflow.py`、`versioning.py` 及必要的协作读取代码：
  新旧任务分派、缺项输出、升级后的下一步提示。
- `skills/matt-to-tickets/SKILL.md`、`skills/matt-implement-spec/SKILL.md` 及必要的实现入口：
  修正默认标签、无依赖即可实施的表述与模板，同步 `upstream/matt.patch`，继续核对来源一致性。
- 对应测试与设计、验收文档：保存此次缺陷的回归场景。

工作流可以核对输入、状态和交付材料，但不能拦截代理在任意编辑器里的每次源码写入。
因此必须同时修正技能行为并用真实代理试用验证，不能只凭增加状态字段宣称问题已消失。

## 当时提出的验收要求（旧任务规则已由批准方案替代）

| 场景 | 预期结果 |
| --- | --- |
| 新建 Issue，只有需求和验收项 | 先生成方案；不改业务代码，不派出实施代理 |
| 任务没有前置依赖，但方案仍待确认 | 保持待评审，不自动标为可实施 |
| 中等或复杂任务，方案未获批 | 可以调查与复现，实施条件为不满足 |
| 用户仅确认业务问题或部分字段 | 只记录对应确认，其余方案仍待评审 |
| 方案已批准、任务已指派，换会话或换人 | 核对共享材料后直接继续，不重复请求同一批准 |
| 简单任务采用现有合并评审路径 | 先有简短方案和有依据的评估，之后可以实施；交付前核对合并评审 |
| 第四版项目中新建旧格式任务 | 报告缺少延续依据，不能静默进入已确认的旧流程 |
| 真实旧任务继续处理 | 保留原格式与原规则；不自动迁移或要求重新批准已接受范围 |
| 已确认字段后新增跨服务设计 | 保留字段批准，对新增影响部分形成方案并评审 |
| 工具升级、长会话继续 | 重新读取现行入口；新任务从当前模板开始 |

实施后运行完整单元测试、发行检查，以及远端 CS 默认分支的真实接口与并行组合检查。
按仓库规则在隔离工作区进行独立代理试用，分别检查“只有 Issue”“已有批准”“简单任务”
和“新任务沿用旧格式”的真实动作与结果。代理试用仍不能替代两位真实团队成员的试点。
